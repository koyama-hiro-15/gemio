# サンドボックス実行環境・トラストモードおよび開発者モード アーキテクチャ設計書

**作成日:** 2026年11月02日  
**最終更新日:** 2026年11月11日  
**ステータス:** 実装完了  
**対象システム:** `src/gemio/project/base.py`, `src/gemio/project/developer.py`, `src/gemio/core/agent.py`, `src/gemio/core/prompts.py`, `src/gemio/cli/main.py`, `src/gemio/cli/ui.py`  

### 【要約】
Gemioを非開発者の日常業務から多言語ソフトウェア開発まで安全・汎用的に対応させるため、「基本モード（`Project`）」と「開発者モード（`DeveloperProject`）」の2層実行環境と、プロジェクトの信頼度に応じた「通常承認モード」と「トラストモード（`--trust` / `/trust`）」の2軸アーキテクチャを定義します。また、ホストOS上でのシェル誤実行の完全防止、コンテナセキュリティの3段階境界基準（起動拒否 / 強い警告 / 注意警告）、`in_container` と `host_docker` 両モードにおける値を読み取らないAPIキー・機密環境変数検査と強い警告通知、セキュア入力・メモリ保護機構、多言語環境向けの除外・機密保護ルール、および承認拒否を無視した暴走を阻止するサーキットブレーカー機構を規定します。

## 1. 背景と目的（リスクベースの安全設計）

1. **脅威の源泉に応じた合理的なリスク管理（トラストモードの導入）**:
   * **未知・外部の信用できないプロジェクト**（プロンプトインジェクション等のリスクあり）を扱う際は、**「通常承認モード」**によって人間の目（Human-in-the-loop）とサーキットブレーカーで確実に操作を制御する。
   * **開発者自身が作成したプロジェクトや安全確認済みのプロジェクト**においては、AIは悪意ある行動をとらないため、**「トラストモード（`--trust` / `/trust`）」**によって承認プロンプトなしで自由かつ高速に自律作業を行わせる。
   * トラストモード時に起こり得る「善意のうっかりミス（ホストOS環境の汚染や `.env` の誤上書き等）」は、**Dockerコンテナ隔離**と**ファイル保護ガードレール**で物理的・システム的に受け止める。
2. **ホストOSでのシェルコマンド誤実行の完全排除**:
   * 開発者モード（`--dev`）におけるシェルコマンド実行は100%必ずDockerコンテナ内で行い、環境変数の誤設定等によってホストOS上でシェルが直接実行されるリスクを排除する。
3. **Python以外の多言語開発環境への最適化**:
   * Node.js / TypeScript, Go, Rust, Java, Ruby, PHP, Terraform等のプロジェクトにおいて、`node_modules` や `target` 等の巨大ディレクトリ走査除外、多言語の認証ファイル保護、環境変数スクラブに対応する。

## 4. 開発者モード（DeveloperProject）とコンテナ境界の厳格化

開発者モードは、CLI起動時に `--dev` オプションが**明示的に指定された場合のみ**有効となります。

### 4.1 起動・実行形態の厳格な判定（In-Container / Host-Orchestrated）

```text
[ DeveloperProject 起動時判定 ]
       │
       ├─ (A) コンテナ内部で起動されている場合 (in_container)
       │     条件: sys.platform == "linux" かつ (/.dockerenv または /run/.containerenv が存在)
       │     ├─ 1. コンテナ脱獄リスクの検査（特権モードでないか、docker.sockがないか -> 違反時は起動拒否）
       │     ├─ 2. prctl(PR_SET_DUMPABLE, 0) で子プロセスからのメモリ読み取りを遮断
       │     ├─ 3. コンテナ内の機密環境変数（APIキー等）のキー名検査（値は読み取らず、検出時は強い警告）
       │     ├─ 4. 環境変数にGemini APIキーが未設定なら起動時セキュア入力プロンプト (****マスク) で取得
       │     └─ 5. コンテナ内の /bin/bash (または /bin/sh) をクリーンな subprocess で実行
       │
       └─ (B) ホストOS上で起動されている場合 (host_docker)
             ├─ 1. ホストOSのシェル直接実行は【絶対禁止】
             ├─ 2. 対象コンテナの稼働と脱獄リスク設定を inspect 検査（違反時は起動拒否）
             ├─ 3. コンテナ内の機密環境変数（APIキー等）のキー名検査（値は読み取らず、検出時は強い警告）
             └─ 4. docker exec 経由でコンテナ内部へコマンドを委譲実行
                   （※Gemio用のAPIキーはホスト側環境変数・メモリのみに留まり、コンテナ内へ渡らない）
```

* **環境変数偽装の排除**:
  `_is_running_in_container()` は環境変数（`DEVCONTAINER` 等）に依存せず、`sys.platform == "linux"` かつ `/.dockerenv` または `/run/.containerenv` の実在のみを基準とします。これにより、Windows / macOS ホストや生身のLinuxホストで誤ってローカルシェルが実行される可能性をゼロにします。
* **コンテナのセキュリティ検査 (`_validate_in_container_security` / `_validate_and_configure_docker_container`)**:
  * コンテナが稼働中（`State.Running == True`）であること。
  * 特権モードでないこと（`HostConfig.Privileged == False` / `CapEff` 全有効マスクでないこと）。
  * ホストネットワーク共有モードでないこと（`HostConfig.NetworkMode != "host"`）。※コンテナの外部通信が不要な場合は `--network none` での起動を推奨。
  * `Mounts` またはコンテナ内に `docker.sock` やホストのルートディレクトリ（`/`, `C:\`）が含まれていないこと。

### 4.2 コンテナセキュリティの3段階境界基準（起動拒否 / 強い警告 / 注意警告）

開発者の利便性（テスト対象アプリでのAPIキー利用等）を妨げず、かつ致命的なホスト破壊や機密漏洩リスクを確実に制御するため、`in_container` と `host_docker` の両モードで一貫した**3段階のセキュリティ境界基準**を適用します。

#### 基本基準
1. **🚫 起動拒否（`SandboxSecurityError` / ハードブロック）**
   * **基準**: **「サンドボックスの壁そのものが存在しない、またはコンテナ脱獄（ホストOSの乗っ取り・直接破壊）が可能な状態」**
   * 開発上のいかなる理由があっても許容できず、そのまま動かすとホストOS自体が危険に晒されるケースのみを起動拒否とします。
2. **🔴 強い警告（`danger` アラート / 赤枠パネル表示）**
   * **基準**: **「コンテナへの隔離は成立しているが、コンテナ内部に機密情報（各種APIキー環境変数や `.env`、秘密鍵）が露出しており、AIがシェル経由で読み取れるリスクがある状態」**
   * 開発対象アプリのテスト等で意図的に設定・配置しているケースもあるため起動は止めず、`--dev` 起動直後の診断パネル（および `/sandbox` コマンド）にて赤枠で強く警告します。
3. **🟡 注意警告（`warning` アラート / 黄枠パネル表示）**
   * **基準**: **「機密情報の漏洩ではないが、ホスト側とのファイル権限競合やバイナリ汚染、設定ファイルの誤改ざんなど、開発環境の破損につながる状態」**

#### 起動拒否と警告の境界マトリクス（両モード共通基準）

| 判定区分 | 検査項目 | `in_container`<br>(コンテナ内起動) | `host_docker`<br>(ホストOS起動) | 理由・目的 |
| :--- | :--- | :---: | :---: | :--- |
| **🚫 起動拒否**<br>(`SandboxSecurityError`) | **コンテナ未稼働 / Docker未検出** | － | **起動拒否** | ホストOS上で直接シェルコマンドを実行させないため |
| **🚫 起動拒否**<br>(`SandboxSecurityError`) | **特権モード (`--privileged`)** | **起動拒否** | **起動拒否** | コンテナを脱獄してホストOSの全デバイス・カーネルを操作できるため |
| **🚫 起動拒否**<br>(`SandboxSecurityError`) | **Dockerソケット (`docker.sock`) マウント** | **起動拒否** | **起動拒否** | コンテナ内からホストのDockerデーモンを操り、ホストroot権限を奪えるため |
| **🚫 起動拒否**<br>(`SandboxSecurityError`) | **ホストネットワーク共有 (`--network host`)** | － *(※1)* | **起動拒否** | ホストOSのローカル通信・全ポートに無制限アクセスできるため |
| **🚫 起動拒否**<br>(`SandboxSecurityError`) | **ホストルート (`/` や `C:\`) の直接マウント** | － *(※1)* | **起動拒否** | ホストOSの全ファイルシステムがコンテナ内に丸見え・書き換え可能になるため |
| **🔴 強い警告**<br>(`danger` / 赤枠) | **コンテナ内環境変数への各種APIキー・トークン設定**<br>(`GEMINI_API_KEY`, `OPENAI_API_KEY`, `*_TOKEN`, `*_SECRET` 等) | **🔴 強い警告** | **🔴 強い警告** | シェルや `/proc/*/environ` から値が読まれるリスクがある一方、テスト対象アプリで必要な場合もあるため |
| **🔴 強い警告**<br>(`danger` / 赤枠) | **機密ファイル・フォルダの未マスク露出**<br>(`.env`, `*.pem`, `*.key`, `id_rsa`, `.aws/`, `.ssh/` 等が `/dev/null` や `tmpfs` で保護されていない) | **🔴 強い警告** | **🔴 強い警告** | シェルコマンド（`cat .env` 等）でコンテナ内から中身を読み取られるリスクがあるため |
| **🟡 注意警告**<br>(`warning` / 黄枠) | **コンテナ実行ユーザーが `root` (UID=0)** | **🟡 注意警告** | **🟡 注意警告** | 作成されたファイルがホスト側で `root` 所有になり編集不能になるリスクがあるため |
| **🟡 注意警告**<br>(`warning` / 黄枠) | **管理・設定ファイルの書き込み可能 (`rw`) マウント**<br>(`.git/`, `Dockerfile`, `compose.yaml`, `pyproject.toml` 等が `:ro` でない) | **🟡 注意警告** | **🟡 注意警告** | シェルやテスト実行中にAIが設定やGit履歴を誤って書き換えるリスクがあるため |
| **🟡 注意警告**<br>(`warning` / 黄枠) | **仮想環境・依存キャッシュのホスト共有 (`rw`)**<br>(`.venv/`, `node_modules/`, `target/` 等が専用ボリューム隔離されていない) | **🟡 注意警告** | **🟡 注意警告** | ホストOS（Windows/macOS）とコンテナ（Linux）のバイナリが混ざって環境が壊れるため |

*(※1 `in_container` モードではコンテナ内部からホスト側のマウント元パスや `--network host` フラグ自体を直接確定できないため、ネットワーク状態やマウント状態は診断パネル上で可視化します)*

### 4.3 コンテナ内APIキー・機密環境変数の統一検査と警告通知設計（値を読み取らない安全検査）

`in_container` と `host_docker` の両モードにおいて、コンテナ内に設定されている各種APIキー・機密トークン環境変数を**「値は一切読み取らず（保持・表示せず）キー名のみを検出」**し、強い警告（`danger`）として通知します。

#### 1. 検査対象とする環境変数の範囲（`is_sensitive_env_key(key: str) -> bool`）
`scrub_environment()` と同一の基準で以下の環境変数名を検査対象とします。
* **完全一致 (`SCRUBBED_ENV_KEYS`)**:
  `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AZURE_CLIENT_SECRET`, `GITHUB_TOKEN`, `GH_TOKEN`, `GITLAB_TOKEN`, `NPM_TOKEN`, `NODE_AUTH_TOKEN`, `PYPI_TOKEN`, `CARGO_REGISTRY_TOKEN`, `GEM_HOST_API_KEY`, `COMPOSER_AUTH`
* **末尾一致 (`SCRUBBED_ENV_SUFFIXES`)**:
  `*_API_KEY`, `*_SECRET`, `*_SECRET_KEY`, `*_TOKEN`, `*_PASSWORD`, `*_PRIVATE_KEY`

#### 2. モード別の検出方法（値を読み取らない・メモリに残さない仕組み）
`DeveloperProject._detect_container_sensitive_env_keys()` を実装し、以下の方法で空でない機密環境変数のキー名リスト（ソート済み・重複なし）を取得します。

* **(A) `in_container` モード（コンテナ内起動時）**:
  1. `os.environ`: キー名（`os.environ.keys()`）を走査し、`is_sensitive_env_key(k)` が `True` かつ値が空でない（`bool(os.environ.get(k, "").strip())`）場合、**キー名 `k` のみ**を抽出します。
  2. `/proc/1/environ`: バイト列を `\x00` で分割し、`=` の左辺（キー名）と右辺が空でないこと（`len(val_bytes.strip()) > 0`）のみを確認して、値部分はデコード・保持せず**キー名のみ**を抽出します。
* **(B) `host_docker` モード（ホストOSからコンテナ接続時）**:
  1. **コンテナ内プローブ (`_probe_container_via_exec()`) でのキー名のみ抽出**:
     `docker exec` のプローブコマンドにて、値を出力せず「値が空でない環境変数のキー名だけ」を列挙し、平文のAPIキー値を標準出力やPythonメモリに一切流さずにキー名リストを取得します。
  2. **`docker inspect` 結果（`Config.Env`）のサニタイズ保護**:
     `_validate_and_configure_docker_container()` および `inspect_sandbox_status()` で `docker inspect` を実行した際、取得したJSON内の `Config.Env`（`"KEY=VALUE"` の配列）は直ちに値部分をマスク（値が空でない場合は `"KEY=<redacted>"`、空の場合は `"KEY="`）してから `self._last_inspect_info` に保存します。プローブが実行できない場合のフォールバックとしてもこのマスク済み情報からキー名のみを判定します。

#### 3. `in_container` 起動時のセキュアAPIキー入力プロンプトとの連携
* コンテナ内環境変数に `GEMINI_API_KEY` および `GOOGLE_API_KEY` が**未設定の場合（推奨運用）**:
  従来通り、起動時に `prompt_api_key_for_container()` を呼び出し、`****` マスク入力で安全にAPIキーを受け取ってオンメモリで `AIChatAgent` に渡します。
* コンテナ内環境変数に `GEMINI_API_KEY` または `GOOGLE_API_KEY` が**既に設定されている場合**:
  起動拒否は行わず、2重入力を避けるため `prompt_api_key_for_container()` をスキップして起動を継続し、直後の診断パネルで `🔴 危険 (danger)` の強い警告を表示します。

#### 4. 診断パネル（`print_sandbox_status_panel`）での表示仕様
* **【1. コンテナ基本設定】**:
  * 未検出時: `• コンテナ環境変数 : 🟢 機密キー検出なし`
  * 検出時: `• コンテナ環境変数 : 🔴 機密キー検出あり (GEMINI_API_KEY, OPENAI_API_KEY)`（※キー名のみ表示）
* **【3. セキュリティ・マウント診断アラート】**:
  * `level: "danger"`（🔴 危険）として警告を追加し、パネル枠線を赤色（`border_style="red"`）にして、検出されたキー名とリスク（`env` や `/proc/*/environ` からの読み取りリスク）および対策（`compose.yaml` / `devcontainer.json` / `docker run -e` からの削除推奨）を明示します。

## 5. 通常承認モード・トラストモードとガードレール設計

### 5.1 通常承認モード vs トラストモード

| モード | 指定方法 | 対象プロジェクトと動作仕様 |
| :--- | :--- | :--- |
| **通常承認モード**<br>（デフォルト） | 指定なし<br>（または `/trust off`） | **未知・外部のプロジェクト、または慎重に確認したい作業向け**。<br>ファイルの変更・削除・移動・コピー、およびシェルコマンド実行のたびに **Human-in-the-loop（承認プロンプト）** を表示する。 |
| **トラストモード**<br>（Trust Mode） | CLI引数 `--trust`<br>または `/trust` コマンド<br>*(互換: `--auto` / `/auto`)* | **自作プロジェクトや安全性が確認済みの信頼できるプロジェクト向け**。<br>起動時（または切替時）にユーザーの同意を得た上で、以降のファイル変更やサンドボックス内コマンド実行を事前確認なしで高速に自動実行する。 |

### 5.2 全モード共通のセーフティ・ガードレール（うっかり事故の防止）
通常承認モード・トラストモードを問わず、AIのうっかりミスによる事故を防ぐため以下の操作はシステムレベルでブロックします。

1. **プロジェクトルート外へのアクセス防止**:
   * `../` 等によるルート外参照、およびプロジェクト外を指すシンボリックリンクの参照・操作。
2. **多言語・クラウド機密ファイル（`SECRET_FILE_PATTERNS`）の保護**:
   * **環境変数**: `.env`, `.env.*`（※ただしテンプレート用の `.env.example`, `.env.sample`, `.env.template`, `.env.dist` は読み書き許可）
   * **秘密鍵・証明書・キーストア**: `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.ppk`, `*.keystore`, `*.jks`, `*.kdbx`, `id_rsa*`, `id_ed25519*`, `id_ecdsa*`, `id_dsa*`
   * **パッケージマネージャ・フレームワーク認証**: `.npmrc`, `.pypirc`, `.netrc`, `auth.json`, `master.key`
   * **クラウド・インフラ認証**: `*credentials*.json`, `*service-account*.json`, `client_secret*.json`, `*.tfstate`, `*.tfstate.*`, `kubeconfig`
   * ※ディレクトリごと削除・リネームする際も、配下に上記ファイルが含まれる場合はブロックします。またシステムプロンプトにより、シェルコマンド経由での迂回アクセスも禁止します。
3. **`.git/` 管理領域、既存 `.devcontainer/`、および `*.egg-info/` の保護**:
   * `.git/` 配下への直接ファイル読み書き・削除をブロック。
   * `.devcontainer/` が既に存在する場合の設定変更・削除・ファイル追加をブロック（未作成時の新規作成のみ許可）。
   * パッケージ生成メタデータ領域（`*.egg-info/`）への直接変更・削除をブロック。

## 6. ツール呼び出し・承認要求メッセージの情報拡充と巨大データ省略

* **ツール呼び出しログ（`Agent Log`）**: 引数の長文テキストを自動で `[文字数/行数]` と先頭スニペットに省略して表示。
* **承認要求パネル（`Human-in-the-loop`）**:
  * **ファイル書き込み・置換**: データ規模（文字数・行数）と先頭最大10行（500文字）のプレビューを表示。
  * **`run_sandbox_command`（シェルコマンド実行）**:
    * `description` 引数でコマンドの意図・目的の短い説明（100文字以内をプロンプトで指示、150文字超過時は先頭150文字＋`...` に切り詰め、未指定時は `(説明なし)` と表示）を受け取り、承認パネル上に `説明: ...` として表示。
    * 実行環境、作業ディレクトリ、タイムアウトに加え、Pythonスクリプトのワンライナー等でも処理内容全体を人間が把握できるよう、**実行コマンド文字列はトリミング（省略）せず全文を表示**（コマンド前後の括弧装飾も付与しない）。

## 7. 暴走防止：強制作業中止（サーキットブレーカー）＆プロセスキル機構

* **4択承認アクション**: `y` (許可) / `n` (拒否) / `a` (作業強制中止: `AgentExecutionAborted`) / `k` (プロセス即時終了: 実行中のコンテナ子プロセスもキルして `sys.exit(1)`).
* **サーキットブレーカー**: ユーザーが `n`（拒否）を選択した直後、AIがユーザーへの報告を行わずに連続して変更系ツールやコマンド実行を呼び出そうとした場合、自動的に `AgentExecutionAborted` を送出して作業ループを強制停止します。
