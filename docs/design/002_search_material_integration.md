# #002 Web検索結果の「作業前提資料」分離・統合 設計書および検証手順

**作成日:** 2026年10月30日  
**最終更新日:** 2026年11月17日  
**ステータス:** 一部更新（#013 参照）  
**対象システム:** `src/gemio/core/agent.py`, `src/gemio/core/prompts.py`, `src/gemio/cli/main.py`, `src/gemio/cli/ui.py`  

### 【要約】
Google Search GroundingによるWeb検索結果を通常の会話履歴（`chat_history`）から切り離し、セッション内で蓄積・保持する独立ストレージ（`search_materials`）へ分離した上で、通常プロンプト実行時に先頭へ「作業前提資料」として自動合成（インジェクション）する仕様および検証手順を定義します。

> **💡 現行仕様に関する注記:** 検索結果を会話履歴から切り離してプロンプト先頭へインジェクションする基本仕様およびリダイレクトURL除外仕様は現在も有効ですが、内部のデータ構造（旧 `AIChatAgent.search_materials`）は後続の [`013_core_package_refactoring.md`](./013_core_package_refactoring.md) にて `MaterialStore` / `ChatSession`（物理パス非保持・SHA-256重複排除）へ刷新されています。現行仕様は [`manuals/07_ARCHITECTURE_REFERENCE.md`](../../manuals/07_ARCHITECTURE_REFERENCE.md) を参照してください。

---

## 1. 改修の背景と目的

### (1) 現状の課題（違和感の本質的要因）
Google Search Groundingによって取得した検索結果を、通常の会話履歴（`chat_history`）にフラットな発話ターン（`role="model"`）として追加していました。
この方式には以下の課題が存在しました：

1. **時間軸・前提環境の混濁:**
   外部検索から得た「将来仕様（例: Python 3.15のPEP）」や「特定環境向けのドキュメント」が、プロジェクトローカルの現行環境（例: Python 3.11）や安定版の仕様と同じレイヤーに混ざる。
2. **AIの過剰な自己批判（Self-Correction）の誘発:**
   検索後に現行環境・安定版に関する質問・作業指示を受けた際、AIが「自分が以前に言ったことと矛盾している」「動かない構文を確定仕様と誤認したハルシネーションだ」と判断し、文脈破綻を起こす。
3. **リダイレクトURLによるトークン浪費:**
   Google Search Groundingの返却するURLは長大な暗号化リダイレクトURL（`vertexaisearch.cloud.google.com/...`）であり、これをAIプロンプトに含めてもドメインの判別すらできず、トークンを無駄に消費していた。

### (2) 改善の目的
- 検索結果を時系列の発話から切り離し、外部から提供された**「客観的な作業前提資料（Reference Materials）」**として位置づける。
- ユーザーから明示的な破棄指示がない限り、**同一セッション内で検索資料を蓄積・保持**する。
- 通常プロンプト実行時に、蓄積された資料を**プロンプトの先頭に付加（インジェクション）**してAIに提供する。
- コーディング用途のみならず、汎用的なリサーチ・文章作成等でも安定して機能する設計とする。

## 2. アーキテクチャおよび詳細仕様

### (1) データ保持構造 (`src/gemio/core/agent.py`)

`AIChatAgent` に参照資料ストレージ `search_materials` を追加します。

```python
self.search_materials: list[dict[str, Any]] = []
```

格納する要素の構造：
```python
{
    "query": str,               # 検索クエリ (例: "Python 3.15 新機能")
    "response_text": str,       # 検索で得られた回答・要約本文
    "sources": list[dict],      # [{"title": str, "url": str}] 元の出典メタデータ
    "created_at": str,          # 取得時刻 (HH:MM:SS)
}
```

### (2) プロンプト先頭インジェクション仕様

`process_prompt` でAIモデルにプロンプトを送信する際、`search_materials` に資料が存在する場合はプロンプト先頭に資料ブロックを合成します。

#### 資料ブロックのフォーマット
- 長大なリダイレクトURLは完全に除外し、**「Webページのタイトル（＋判別可能なドメイン）」のみを簡潔に記載**します。
- これによりトークン消費を抑えつつ、AIが客観的に資料の性質（公式仕様、ドラフト、記事等）を判別できるようにします。

```markdown
【作業前提資料（Web検索による外部最新情報）】
※ 以下はWeb検索によって取得された参照資料です。現在のローカル環境や確定仕様ではなく、
外部ドキュメント・提案仕様・ドラフト・特定バージョン等の前提条件が含まれる場合があります。
手元の環境（安定版）や既存コードと差異がある場合は、時間軸や前提条件の違いとして客観的に整理して扱ってください。

---
[参照資料 1] (取得時刻: 14:20:15)
■ 検索クエリ: Python 3.15 新機能
■ 参照元情報:
  - PEP 810 – Explicit Namespace Packages (peps.python.org)
  - Python 3.15 Release Schedule (docs.python.org)
■ 資料内容:
Python 3.15では、PEP 810に基づく新しい構文提案や...

---
[参照資料 2] (取得時刻: 14:25:30)
■ 検索クエリ: uv build backend 設定
■ 参照元情報:
  - uv Documentation (docs.astral.sh)
■ 資料内容:
uvでのビルド設定はpyproject.tomlに次のように記述します...
--------------------------------------------------

【ユーザーの指示】
先ほど調べた内容を元に、サンプルコードを作成してください。
```

#### 会話履歴（`chat_history`）の保護
- `chat_history` に資料ブロック付きの長文を毎回保存すると、履歴全体が指数関数的に肥大化します。
- したがって、**`chat_history` に記録するユーザー発話は「本来のユーザー入力文」のみ**とし、モデルへのリクエスト生成時（または最新ターンのみ）に資料を合成して渡します。

### (3) コマンドとCLI・UI仕様 (`src/gemio/cli/main.py`, `src/gemio/cli/ui.py`)

#### ① コマンド体系
| コマンド | 動作 |
|---|---|
| `/search <query>` または `/s <query>` | 検索を実行し、結果を画面表示すると同時に `search_materials` に蓄積保持する（`chat_history` には追加しない）。 |
| `/search --clear` または `/search -c` | セッション内に保持されている全参照資料を破棄する。 |
| `/search`（引数なし） | ヘルプメッセージを表示（`--clear` オプションの案内を含む）。 |

#### ② ユーザーへのフィードバック表示
- 検索完了時:
  - 画面上に回答本文および参照元パネル（ブラウザで開けるリダイレクトリンク付き）を表示。
  - 下部に控えめな案内を表示:  
    `💡 検索結果を参照資料 [N件目] としてセッションに保持しました。以降の通常プロンプトの前提資料として自動参照されます。（破棄: /search --clear）`
- クリア実行時:
  - `保持していた参照資料（N件）を破棄しました。` と緑色で明示。

### (4) システムプロンプト（インストラクション）の改修

`src/gemio/core/prompts.py` の通常プロンプト用 `DEFAULT_SYSTEM_INSTRUCTION` に以下のガイドラインを追加します：

```text
【作業前提資料の取り扱いに関するルール】
- ユーザープロンプトの先頭に【作業前提資料（Web検索による外部最新情報）】が付加されている場合があります。
- これは外部Web検索から提供された客観的な「参考資料」です。現在のローカル環境や確定仕様ではなく、
  将来の提案仕様、ドラフト、特定バージョン/環境に限定された前提条件が含まれる場合があります。
- 手元の現行環境（安定版）や既存コードと差異がある場合でも、自己矛盾やエラーと誤認せず、
  「資料に記載された前提」と「手元の実態」の時間軸やスコープの違いとして客観的に整理し、指示を実行してください。
```

## 3. 実装ステップと検証手順

### ステップ 1: エージェント層の実装と単体テスト (`src/gemio/core/agent.py`)

#### 実装項目
1. `__init__` に `self.search_materials: list[dict[str, Any]] = []` を追加。
2. ユーティリティメソッドの実装:
   - `add_search_material(query, response_text, sources)`
   - `clear_search_materials() -> int`
   - `get_formatted_search_materials() -> str`（URLリダイレクトを除外し、タイトル/ドメインと本文を整形）
3. `process_search_prompt`:
   - `self.chat_history.append(...)` を**削除**。
   - `self.add_search_material(...)` を呼び出すように変更。
4. `process_prompt` / `_execute_agent_loop`:
   - `search_materials` が存在する場合、API送信時に資料ブロックを先頭付加。
   - `chat_history` の肥大化を防ぐ設計の適用。

#### 検証手順（自動テスト）
`tests/test_agent_search.py` を更新し、以下を実行：
```bash
pytest tests/test_agent_search.py
```
- **検証項目 A:** `process_search_prompt` 実行後、`agent.chat_history` が空（0件）のままであり、`agent.search_materials` に1件追加されていること。
- **検証項目 B:** 複数回 `process_search_prompt` を実行した場合、`agent.search_materials` に順次蓄積されること。
- **検証項目 C:** `agent.clear_search_materials()` で資料が空になり、件数が返ること。
- **検証項目 D:** `get_formatted_search_materials()` の出力にリダイレクトURL（`vertexaisearch...`）が含まれず、タイトルと本文が含まれていること。
- **検証項目 E:** `process_prompt` 実行時、APIリクエストのコンテンツ先頭に作業前提資料が付加されていること。

### ステップ 3: 結合・シナリオ検証

#### シナリオ 1: 複数回検索と資料の蓄積
1. `/search Python 3.15 新機能` を実行。
   - 資料 1 件目として保持された旨が表示されること。
2. `/search uv 設定方法` を実行。
   - 資料 2 件目として保持された旨が表示されること。
3. 通常プロンプト「先ほどの内容をまとめて」を実行。
   - AIが資料1と資料2の両方を参照して回答できること。
   - 会話履歴が異常に肥大化していないこと。

#### シナリオ 2: 資料の破棄
1. `/search --clear` を実行。
   - 「保持していた参照資料（2件）を破棄しました。」と表示されること。
2. その後の通常プロンプトでは資料ブロックが付加されないこと。

## 4. 本改修による効果まとめ

| 項目 | 改修前 | 改修後 |
|---|---|---|
| **対話文脈（`chat_history`）** | 検索結果が生ログとして混入し、手元環境と衝突 | 時系列会話のみが綺麗に保たれ、文脈衝突ゼロ |
| **資料のライフサイクル** | 単発の検索で履歴に埋もれる | セッション中保持され、段階的な複数検索に対応 |
| **AIの自己批判** | 「動かない構文を確定仕様と誤認した」と自責破綻 | 「外部から提供された参考資料」として客観的に解釈 |
| **トークン消費** | 暗号化リダイレクトURLを大量消費 | タイトル＋ドメインのみ抽出し、大幅にトークン削減 |
| **用途の汎用性** | コーディング特化になりがち | リサーチ・文書作成・要約など汎用用途にも完全適合 |
