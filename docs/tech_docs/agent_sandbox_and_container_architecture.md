## 1. Claude Codeのコア設計思想

Anthropicが提供するエージェント型CLIツール「Claude Code」は、公式技術資料（『Claude Code: Best practices for agentic coding』『Seeing Like an Agent』など）に示されているように、明確な哲学と原則に基づいて設計されています。

その根底にある設計思想は、主に以下の6点に集約されます。

### 1.1 「低レベル」かつ「非固執的（Unopinionated）」なパワーツール
* **ワークフローの非強制**: 特定の統合開発環境（IDE）、独自UI、固定された開発フローを開発者に強制しません。
* **素の推論能力への直結**: Claudeモデルの素の推論・行動能力に極力近い形でアクセスさせ、パイプライン、シェルスクリプト、チーム独自の開発ルールと自由に結合できる「スクリプト可能な職人向けツール（Power Tool）」として設計されています。

### 1.2 肥大化したフレームワークではなく「エージェント・ハーネス（Agentic Harness）」
* **ブラックボックスの排除**: 複雑で巨大な自律実行エンジンを目指すのではなく、本質は**LLM（Claude）という強力な知能を安全に乗りこなすための「手綱（ハーネス）」**です。
* **最小限の足場提供**: システムの役割を、LLMが自律的にタスクを完了できる「ツール実行環境」「コンテキスト管理」「ファイル入出力」などの最小限かつ堅牢な土台の提供に限定しています。

### 1.3 ターミナルファースト（開発者の生活圏での動作）
* **開発者の日常環境との融合**: 専用GUIを排し、ターミナル（CLI）を起点に設計。既存のシェル環境、Git、ローカルファイルシステム、CLIツール群とシームレスに連携します。
* **Unixパイプライン・CI/CD統合**: 出力を他のUnixコマンドへパイプしたり、CI/CDスクリプト内で自動実行したりといった、開発環境の自動化チェーンに直接組み込める柔軟性を持ちます。

### 1.4 コンテキストウィンドウの節約と最適化（Context-First）
* **有限なリソースの効率活用**: 「コンテキストウィンドウは有限であり、無駄な情報で埋まるほど推論精度・速度・コストが劣化する」という前提から逆算して設計されています。
* **Just-In-Time取得**: ファイル全体を無差別に読み込ませず、必要最小限の差分取得やピンポイント検索（grep/glob等）を実行。
* **`CLAUDE.md` による誘導**: リポジトリの規約やコマンドを簡潔に定義した `CLAUDE.md` を起点に、必要な情報のみを段階的に引き出す構成を採っています。

### 1.5 「エージェントの視点で見る（Seeing Like an Agent）」ツール設計
* **LLM視点のUI**: 人間にとって扱いやすいUIと、LLMにとって誤認しにくく実行しやすいツールインターフェースは異なります。
* **厳選されたプリミティブツール**: 何十個もの細分化されたツールを持たせるのではなく、モデルが誤解しにくい**厳選された約20個のシンプルなツール群**（Bash実行、ファイル読み取り、ピンポイント編集、タスク管理など）で構成。過剰な抽象化を避け、Bash等の基本道具を正しく扱わせるほうが汎用性と堅牢性が高まります。

### 1.6 自律ループ（Agentic Loop）と安全性の境界（Permission Boundaries）
* **フィードバックループの自律反復**: 「指示 → 一括生成」ではなく、「状況把握（Gather Context）→ 実行（Take Action）→ 検証（Verify Results）」のループを自律的に反復します。
* **安全性の境界**: テストの失敗を自律修復する一方、破壊的コマンド、ファイル書き換え、外部通信などに対しては人間が介入して許可・拒否できる承認境界（Permission Boundary）を設けています。

## 2. エージェントにシェルコマンド（Bash）を使わせる理由

Anthropicが個別の特化ツールを細分化して量産せず、「エージェントにシェルコマンド（Bash）を直接使わせる設計」を選択した背景には、Unix哲学、LLMの学習特性、コンテキスト効率の観点から明確な論理が存在します。

```text
[ 従来のアプローチ (個別API量産) ]
エージェント ──> [Git Tool] / [Search Tool] / [Build Tool] / [Test Tool] ... (保守肥大化・モデルの誤認増)

[ Claude Codeのアプローチ (Unix哲学) ]
エージェント ──> [ Bash Tool (単一のプリミティブ) ] ──> git, grep, jq, npm, cargo, pytest...
```

### 2.1 「Bash is All You Need」— 最小の道具による最大汎用性
機能ごとに「ファイル検索ツール」「Git操作ツール」などを細かく実装すると、ツールの保守コストが増大し、機能の組み合わせが難しくなります。Bashという単一のプリミティブを与えることで、CLIに存在する無数の既存ツール（`git`, `grep`, `jq`, `npm`, `curl` 等）をパイプラインで自在に合成（Compose）できます。

### 2.2 LLMが事前学習で「Unixコマンド」を最も深く理解している
『Seeing Like an Agent』の思想に基づき、LLMは学習データの中で膨大なシェルスクリプト、コマンド履歴、Stack OverflowのQA、GitHubのコードを読み込んでいます。人間が新たに定義した独自JSONスキーマのツールよりも、**モデルが既に熟知している標準Unixコマンド群を扱わせるほうが推論エラーや誤認が圧倒的に少ない**という実証的判断に基づきます。

### 2.3 コンテキスト（トークン）の節約とJust-In-Time取得
巨大なコードベースをRAG（ベクトル検索）や一括読み込みでコンテキストに投入すると、トークンを激しく浪費し、インデックスの陳腐化（Stale Index）を招きます。エージェント自身に `grep`, `find`, `head`, `git diff` を実行させれば、**必要な箇所の数行〜数十行だけをピンポイントかつ最新の状態で取得**でき、コンテキスト効率と精度の両立が図れます。

### 2.4 「自律検証（Self-Verification）」ループの成立
エージェントの真価は単なるコード生成ではなく、「動くまで自律修正する」能力にあります。`npm test`、`cargo check`、`pytest` などのコマンドを実行し、エラー出力を標準エラー出力（stderr）から読み取って修正を反復するには、開発者と同じコマンドライン実行能力が不可欠です。

### 2.5 既存の環境・スクリプト資産の継承
開発環境の環境変数、PATH、プロジェクト固有のシェルスクリプト（`make dev` 等）をそのまま流用できます。エージェント専用のプラグインを用意せずとも、`CLAUDE.md` に数行の手順を記すだけで人間と同一の手順を再現させることが可能です。

## 3. サンドボックスアーキテクチャの比較：bubblewrap vs Docker

Claude Codeをはじめとするエージェント実行環境では、「OSネイティブの軽量サンドボックス（bubblewrap / Seatbelt）」と「独立コンテナ（Docker）」の2つのアプローチが存在します。

### 3.1 Claude Code組み込みサンドボックスの構造
Claude Code本体（Node.jsプロセス）はホストマシン上で直接動作します。その上で、実行されるコマンドに対してOSネイティブの隔離機構（オープンソース `@anthropic-ai/sandbox-runtime`）を適用しています。

* **macOS:** OS標準の「Seatbelt（`sandbox-exec`）」フレームワーク
* **Linux / WSL2:** 「`bubblewrap`（名前空間・ファイルシステム分離）」＋「`socat`（プロキシ通信制御）」

#### サンドボックスの内外境界
* **隔離内（サンドボックス対象）**: Bashツールによって実行されるシェルコマンドおよびその子プロセス。作業ディレクトリ外の機密パス（`~/.ssh` など）への書き込みや、未許可ホストへの外部通信を遮断。
* **隔離外（ホスト権限で動作）**: Claude Code内蔵のファイル操作ツール（Read/Edit/Write、パーミッション管理で保護）、MCPサーバー、ユーザーが明示的にエスケープしたコマンド。

### 3.2 bubblewrap と Dockerコンテナの比較

| 比較項目 | bubblewrap (bwrap) | Docker コンテナ |
| :--- | :--- | :--- |
| **隔離レベル** | **プロセス単位**（ホスト環境を制限付き共有） | **OS・ユーザーランド単位**（別環境として隔離） |
| **起動オーバーヘッド** | **極小**（数ミリ秒〜50ms） | **中〜大**（都度起動なら数秒、常駐ならゼロ） |
| **ファイルI/O速度** | **ネイティブ同等**（Linuxホスト上で最速） | Linuxはネイティブ。macOS/Winのマウントは遅延大 |
| **安全性（破壊防止）** | 高い（指定外パスへの書き込みは防げる） | **極めて高い**（コンテナ破棄で完全原状復帰） |
| **安全性（機密情報保護）** | 引数設計・設定精度に依存 | 高い（ホストの認証情報を隔離しやすい） |
| **ツールの準備・生産性** | **即時性高**（ホストのPATH/環境を即流用） | **Dockerfileの定義・保守が必要** |
| **ポータビリティ** | **Linux限定**（macOS不可、WinはWSL2必須） | **マルチプラットフォーム共通** |

### 3.3 使い分けの指針
* **bubblewrap方式が適するケース**:
  * LinuxまたはWSL2環境で作業している場合。
  * 開発者がエージェントのログを見ながら**対話的に開発**を進める場合。
  * ホスト上に整備された言語ランタイムやCLIツール群をそのまま活かしたい場合。
* **Dockerコンテナ方式が適するケース**:
  * 未検証のOSSリポジトリや第三者コードを解析・実行する場合。
  * 人間の承認をスキップし、**「完全無人（放置）」で自律走行**させる場合。
  * CI/CDやクラウドサーバー上で再現性のあるワーカーとして動かす場合。

## 4. エージェントに「自由なコンテナ」を与える意義とパフォーマンス

エージェントに「完全隔離されたコンテナ」と「自由な実行権限（root権限等）」を与える構成は、AIの自律的な問題解決能力を極限まで引き出すための有効なアプローチです（SWE-benchやDocker Sandboxes等でも標準採用）。

```text
[ 制約の多い環境 ]
エラー発生 ──> ツール不足/権限不足で停止 ──> 人間の手動対応待ち (ボトルネック)

[ 自由なコンテナ環境 ]
エラー発生 ──> 自律的にツール導入(apt/pip) ──> サービス起動 ──> 動的検証(curl/test) ──> 完遂
```

### 4.1 主なメリット

1. **人間の承認待ちを排除した「超高速自律ループ（Unattended Loop）」**:
   「最悪壊れてもコンテナを破棄すればよい」という前提があるため、`--dangerously-skip-permissions` 等による全自動化が可能。1分間に数十回の試行錯誤を自律反復でき、完了までのリードタイムが劇的に短縮されます。
2. **「自律的な環境構築・自己修復」能力の解放**:
   不足しているコンパイラやCLI（`jq`, `ripgrep`, `lsof`）、デバッグ用解析ツール（`strace`, `gdb`）を自律的に `apt-get` 等で導入し、開発用DB（PostgreSQL/Redis）を立ち上げてテストを通すなど、環境トラブルによる立ち往生を解消します。
3. **「動的検証（実行して確かめる）」による精度の向上**:
   静的なコード閲覧による推測（ハルシネーションの温床）から脱却し、実際にWebサーバーを起動して `curl` やヘッドレスブラウザで振る舞いを検証可能。フィードバック情報が格段に増え、修正精度が向上します。
4. **破壊を恐れない「大胆な仮説検証」**:
   コード全体への乱暴なデバッグログ挿入、依存関係の完全再インストール、大規模リファクタリング後の `git reset` など、安全な小手先の変更にとどまらない本質的な解決策の探索が可能になります。

### 4.2 注意すべき落とし穴とガードレール
* **迷走ループ・トークン浪費**: 解決不能な依存関係エラー等に対して無意味なパッケージ再インストールを繰り返すリスク。「最大ステップ数（Max Steps）」や「タイムアウト時間」を必ず設ける必要があります。
* **ファイルI/O遅延**: 次章の通り、マウント設定を誤るとエージェントの思考速度が大幅に低下します。

## 5. Docker環境におけるパフォーマンスボトルネックと最適化

Dockerの導入は推論モデル自体の知能には影響しませんが、**ファイルI/Oのレイテンシ**がエージェントの処理速度に甚大な影響を及ぼします。

### 5.1 ボトルネックのメカニズム
* **ホストバインドマウントの同期遅延（macOS / Windows）**:
  Docker Desktopでホスト側フォルダを `-v` マウントした場合、仮想化ハイパーバイザー境界を跨ぐファイル同期のオーバーヘッドが発生します。エージェントは `grep`、`find`、ファイル編集、テストを毎分大量に実行するため、1回あたりのI/O遅延が数秒〜十数秒単位で蓄積し、全体の所要時間が激増します。
* **都度起動オーバーヘッド**:
  コマンドを実行するたびに新しくコンテナを立ち上げると、毎回数百ミリ秒〜数秒の起動時間が累積します。

### 5.2 パフォーマンス低下を防ぐ最適化対策

```text
[ 低速パターン (非推奨) ]
Host OS (Win/Mac) ──[ 遅い仮想化マウント ]──> Container ──> エージェント (I/O待ち多発)

[ 高速パターン (推奨) ]
Docker Storage (Named Volume / WSL2 Native) ──[ ネイティブLinux I/O ]──> Container ──> エージェント (高速)
```

1. **ホストOSドライブの直接マウントを避ける**:
   * **Windows (WSL2)**: `C:\Users\...` などのWindowsファイルシステム側ではなく、WSL2内部のLinuxファイルシステム（`\\wsl$\...` や `~/projects/...`）上にリポジトリを配置する。
   * **macOS**: ホストフォルダの直接バインドマウントを避け、Dockerの名前付きボリューム（Named Volume）内にリポジトリを `git clone` して作業させる（Dev Containersの「Clone in Volume」を活用）。または VirtioFS を有効化する。
2. **常駐型コンテナ（Dev Containers）を採用する**:
   コマンド単位で都度コンテナを起動するのではなく、常駐させたコンテナ環境の内部でエージェントを動かすことで起動遅延をゼロ化します。
3. **必要なツール群を事前ビルドしておく**:
   `git`, `curl`, `jq`, 各種言語ランタイムを事前ビルドしたイメージを用意し、実行時にエージェントがツール導入に費やす推論トークンと時間を削減します。

## 6. コンテナサンドボックスのセキュリティ脅威と堅牢化

「Dockerコンテナはサンドボックスとして万能か？」という問いに対しては、**「偶発的な事故防止には極めて有効だが、悪意ある攻撃に対する強固な隔離壁としては不十分」**というのが正確な脅威モデルです。

### 6.1 主な脅威とリスク

```text
               ┌── [ 脅威1: マウントされた .env / Git認証情報の漏洩 ]
               ├── [ 脅威2: ローカルネットワーク (LAN) への不正到達 ]
コンテナ内 ────┼── [ 脅威3: host.docker.internal 経由のホストサービス侵害 ]
エージェント   ├── [ 脅威4: コンテナ内root = ホストroot (カーネルエスケープ) ]
               └── [ 脅威5: /var/run/docker.sock マウントによるホスト完全乗っ取り ]
```

1. **マウントされた機密情報の窃取**:
   ホスト側の作業フォルダをマウントすると、含まれる `.env`（本番APIキー、DB認証情報）やGitクレデンシャルがコンテナから読み取られ、間接的プロンプトインジェクション等によって外部流出するリスクがあります。
2. **ローカルネットワーク（LAN）・ホストOS内サービスへのアクセス**:
   デフォルト設定のDockerはホストの属するLANに通信でき、さらに `host.docker.internal` を経由してホスト上で動くローカルサーバー（開発中Webアプリ、内部DB等）に到達可能です。
3. **「コンテナ内root ＝ ホストOSのroot」問題**:
   デフォルト設定ではコンテナ内UID 0はホストのUID 0と同一です。カーネルやランタイムの脆弱性を突かれた場合、コンテナエスケープによってホストの最高権限が奪取されます。
4. **致命的オプションの併用リスク**:
   * `--privileged`: コンテナ内からホストの全デバイス（`/dev/sda` 等）へアクセス可能となり、ホストOSが乗っ取られます。
   * `/var/run/docker.sock` のマウント: コンテナ内からホストのDockerデーモンを直接制御できるため、ホストのroot権限を渡すのと同義です。

### 6.2 堅牢化対策

#### ① ローカルネットワーク（LAN）アクセスの遮断
外部インターネット（パッケージ取得やLLM API）のみを許可し、LAN・プライベートIP帯へのアクセスを落とします。

* **Linux（`iptables` による制御）**:
  Docker標準の `DOCKER-USER` チェーンを使用し、プライベートIP帯（RFC 1918）宛てのパケットをドロップします。
  ```bash
  # 確立済み接続を許可
  sudo iptables -I DOCKER-USER -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
  # プライベートIP帯へのアクセスを遮断
  sudo iptables -A DOCKER-USER -d 10.0.0.0/8 -j DROP
  sudo iptables -A DOCKER-USER -d 172.16.0.0/12 -j DROP
  sudo iptables -A DOCKER-USER -d 192.168.0.0/16 -j DROP
  ```
* **Docker Desktop（ホストアクセスの無効化）**:
  コンテナ起動時にダミーIPを割り当て、ホスト到達を無効化します。
  ```bash
  docker run --add-host=host.docker.internal:127.0.0.1 ...
  ```
* **完全オフライン実行（最堅牢）**:
  追加通信が不要なリファクタリング作業等では、`--network none` を適用して完全隔離します。

#### ② 権限の最小化と隔離強化
* **Rootless Docker / User Namespaces (`userns-remap`)**:
  コンテナ内部ではroot（UID 0）に見えても、ホストOS上では一般ユーザー（UID 1000等）にマッピングされ、エスケープ時の被害を局所化します。
* **非特権ユーザー ＋ 制限付きsudo**:
  コンテナ内ユーザーを一般ユーザー（`vscode` 等）とし、`apt-get` のみパスワードなしsudoを許可します。
* **Linux Capabilitiesの剥奪**:
  `--cap-drop=ALL` を適用し、不要なカーネル権限を削減します。
* **MicroVM（未信頼コード実行時）**:
  第三者の未検証リポジトリを無人で実行する場合は、カーネルを共有するDockerではなく、ハードウェア仮想化で分離する **MicroVM（Firecracker, E2B, Modal 等）** を選択します。

## 7. 日常リポジトリ開発における推奨ベストプラクティス

日常的に参加している自社・個人のリポジトリ開発においては、「未信頼コード向けの重装備で日常の快適さを損ねないこと」と「ファイルI/O速度・安全な自律性・ホスト/LAN保護の3立」が肝要です。

### 7.1 推奨アーキテクチャ概要
日常開発で最もバランスが優れているのは、**「常駐型Dev Container（非特権ユーザー＋名前付きボリューム/LinuxネイティブI/O）」** です。

```text
[ ホストマシン (Mac / Win / Linux) ]
   │
   ├─ .env / ~/.ssh / ~/.aws (コンテナへ持ち込まない・マウント除外)
   │
   └─ [ 常駐型 Docker コンテナ (Dev Container) ]
         ├─ ユーザー: 非特権ユーザー (UID 1000) + apt-getのみパスワードなしsudo
         ├─ コードベース: Named Volume または Linuxネイティブファイルシステム
         ├─ ネットワーク: LAN遮断 + host.docker.internal無効化
         │
         └─ [ Claude Code (エージェント) ]
               ├─ 実行モード: 自動承認スキップ (--dangerously-skip-permissions)
               └─ ガイド役: CLAUDE.md (ビルド・テスト規約)
```

### 7.2 実践の5箇条

1. **ファイルI/O速度の最優先維持**:
   * Windows (WSL2): リポジトリをWSL2内のLinuxファイルシステム上に配置。
   * macOS: ホストフォルダを直接マウントせず、Dockerの名前付きボリューム上に `git clone` して作業（Dev Containersの「Clone in Volume」）。
2. **非特権ユーザー ＋ パッケージ管理のみsudo許可**:
   * 実行ユーザーは非特権（UID 1000）とし、sudoersで `/usr/bin/apt-get` のみNOPASSWD設定。
   * エージェントの自由なツール追加を許容しつつ、ホスト側ファイルのroot所有権汚染や破壊を防ぐ。
3. **機密情報の遮断**:
   * 本番キーを含む `.env` はコンテナ内に配置せず、ダミーの `.env.example` を配置。
   * ホストの `~/.ssh` や `~/.aws` をマウントせず、コンテナ専用の一時トークンやデプロスキーを使用。
4. **LANおよびホストアクセスの遮断**:
   * `--add-host=host.docker.internal:127.0.0.1` の指定、またはLinuxでの `iptables` 制限を実施。
5. **Gitブランチ分離による無人自律実行**:
   * タスクごとに専用ブランチ（`feature/agent-task`）を作成。
   * `CLAUDE.md` でプロジェクトのテスト手順を指示。
   * `--dangerously-skip-permissions` でエージェントを自律走行させ、作業完了後に人間が `git diff` でレビューする。

### 7.3 OS別・現実的な選択肢まとめ

* **Linux / WSL2 環境**:
  * **手元での対話的開発**: Claude Code組み込みの `bubblewrap` をそのまま利用（オーバーヘッドゼロ、高速）。
  * **完全放置・自動化**: Rootless Docker / 常駐Dev Containerで実行。
* **macOS 環境**:
  * **手元での対話的開発**: ホスト上でそのまま起動し、Seatbeltサンドボックスと手動承認で運用（I/O最速）。
  * **完全放置・自動化**: Dev Container（Named Volume上にリポジトリを配置）内で自律走行。
