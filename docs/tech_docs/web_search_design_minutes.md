# 📝 Gemio Web検索機能 設計検討議事録（Google Search Grounding からの方針転換経緯）

**作成日:** 2026年11月24日  
**最終更新日:** 2026年11月24日  
**ステータス:** 記録確定（設計判断ログ）  
**関連設計書:** [`#016 作業エージェント連携型Web検索`](./../design/016_agent_delegated_web_search.md) ➔ [`#017 人間介在型 Web 検索支援`](./../design/017_human_assisted_web_search.md)  

### 【要約】
Gemio 正式リリースに向けた利用規約適合性レビューの結果、[`#016`](../design/016_agent_delegated_web_search.md) で採用した Google Search Grounding 連携を廃止し、**「人間介在型 Web 検索支援（Human-Assisted Web Search）」**（[`#017`](../design/017_human_assisted_web_search.md)）へ設計方針を転換するに至った検討経緯、却下した代替案と理由、および合意された最終仕様を記録した議事録です。

---

## 1. 検討の背景・議題

* **背景:**
  [`#016`](../design/016_agent_delegated_web_search.md) により、`ChatAgent` から隔離されたステートレス `SearchAgent`（Gemini API の Google Search Grounding）を呼び出す検索連携を実装した。しかし、正式リリース前に **Google 検索グラウンディング利用規約への適合性** を精査したところ、重大な非適合箇所が複数判明したため、リリース可能な設計への見直しを実施した。
* **議題:**
  1. 現行の Google Search Grounding 実装の規約適合性と修正可能性の評価
  2. 代替手段（外部検索 API、ブラウザ自動操作、スクレイピングスクリプト）の実現性評価
  3. 規約・セキュリティ・実用性のすべてを満たす最終方式の決定

---

## 2. 論点 1：Google Search Grounding 利用規約への適合性評価

最新の **Gemini API Additional Terms of Service（2026年3月23日発効版）** および **Grounding with Google Search 公式ドキュメント** を精査した結果、以下の点で Gemio のアーキテクチャと根本的に両立しないことが確認された。

1. **Search Suggestions（`searchEntryPoint.renderedContent`）の無改変表示義務と TUI の限界**
   * 規約上、Grounded Results と関連する Search Suggestions を色・フォント・外観無改変のまま回答幅以上で常時表示し、チップ押下時に直接 Google 検索結果ページ（SRP）へ遷移させる必要がある。
   * 公式仕様は HTML/CSS スニペットの描画を前提としており、ターミナル TUI（Textual）向けのテキスト置換や免除規定は存在しない（書面による Google の個別許可が必須）。
2. **`Agent-as-a-Tool`・`MaterialStore`・`/compact` による加工・保持の制限**
   * 原則として Grounded Results の改変・混在・分析は禁止されている。
   * 2026年3月23日版で「Google の Function Calling 経由で再投入し洗練された Grounded Result を得る」例外が設けられたが、**(i) 他の目的に使わない、(ii) 未表示の中間結果を最終生成後に削除する、(iii) Search Suggestions（最大5件）と Links を最終結果と一緒に表示する** の3条件をすべて満たす必要がある。
   * Gemio のような「検索結果をもとにローカルコードを書き換える」「リダイレクト URL を除外して整形テキストを返す」「`MaterialStore` へ保存して後続の別プロンプトへ注入し続ける」「`/compact` で要約圧縮する」用途は規約想定から外れており、適合困難と判断された。
3. **Links（`groundingChunks[].web.uri`）の表示・保存制限**
   * 現行の `SearchTurnWidget` はドメイン名テキストのみを表示しており直接遷移リンクになっていなかった。また、保存例外は検索結果テキストに限定され、Links の蓄積や別プロンプトへのキャッシュ流用は認められていない。
4. **OSS / BYOK 配布形態との緊張関係**
   * 規約は「自身が所有・運営するアプリ（Owned and Operated by You）」限定、プロフェッショナル・ビジネス用途限定、EEA/スイス/英国ユーザー向けは有料枠限定と定めており、エンドユーザー自身の API キーで動かす OSS クライアント（BYOK）では適合上のリスクが残る。
   * ※ Google Cloud **Vertex AI（Service Specific Terms Section 20.k）** も比較検討し、標準課金かつ 1日100万プロンプト未満なら Search Suggestions 省略が認められる点を確認したが、改変・分析・他目的利用禁止および Function Calling 再投入例外の欠如は同様であり、一般 BYOK ユーザーへの GCP 認証負荷も高いため見送りとなった。

**【小括】**
Google Search Grounding の規約は Web 版 Gemini や検索ページの AI モードと同等の「検索回答のそのまま表示」を想定しており、コーディング/作業エージェントが自律的に検索結果を加工・蓄積して使う Gemio の用途を規約に適合させることは不可能と判断した。

## 3. 論点 2：外部汎用 Web 検索 API（方針 A）の検討

Google Search Grounding を廃止し、LLM 統合を許容する外部検索 API（Tavily、Exa、Perplexity Search API、Brave Search API、Serper 等）へ切り替える案を検討した（※Google Custom Search JSON API は新規受付終了・2027年1月1日完全終了のため対象外、DuckDuckGo 非公式スクレイピングも規約違反のため対象外）。

* **見送りとした理由（実用上の課題）:**
  1. **BYOK における複数 API キー管理・課金負担:**
     ユーザーに `GEMINI_API_KEY` に加えて別サービスのアカウント作成・API キー設定・クレジット管理を求めることになり、導入・運用の実用性が大きく低下する。
  2. **間接プロンプトインジェクション（IPI）リスクの増大:**
     外部検索 API が返す生の Web スニペットや HTML→Markdown 変換テキストには、CSS 非表示領域や HTML コメント、SEO ポイズニング等に仕込まれた悪意ある指示が混入し得る。「外部非信頼入力 ＋ ローカルファイル/シェルアクセス ＋ 変更能力（`EDIT`/`TRUST`）」の同時保有（Lethal Trifecta）により、IPI による不正操作リスクが大幅に上昇する。
  3. **精度とコストのトレードオフ:**
     独自インデックス系は日本語ニッチ情報の網羅性で Google に劣る傾向があり、また検索 API 課金に加えて抽出本文・隔離要約分の Gemini トークン消費が二重に発生する。

## 4. 論点 3：Web ブラウザ自動操作・Python 検索スクリプトの検討

外部有料検索 API を使わず、「Playwright 等でブラウザを Gemio に操作させる」または「Web 検索を行う Python スクリプトを作る」案を検討した。

* **採用不可とした理由:**
  1. **Google 利用規約および `robots.txt` 違反:**
     Google 利用規約（2026年7月30日発効版）および `google.com/robots.txt`（`Disallow: /search`, `Disallow: /goto?`）は、許可なき自動手段での検索アクセスや保護機構の回避を明示的に禁止している。他検索サイトのスクレイピングも同様に規約違反となる。
  2. **技術的な維持不能:**
     2025〜2026年の対策（JavaScript・SearchGuard 必須化、`&num=100` 廃止、`"Verifying your request..."` インタースティシャル、`/goto` リダイレクト）により、従来の HTTP スクレイピングは動作せず、ヘッドレスブラウザも検証ゲートで頻繁に停止する。
  3. **セキュリティリスクが検索 API より深刻:**
     ブラウザ自動操作をエージェントに与えると、DOM/JS クローキングによる IPI、ブラウザプロファイルの Cookie・認証セッション乗っ取り（Same-Origin Policy のエージェント層突破）、SSRF（`localhost` / 社内ネット / クラウドメタデータへの踏み台）、外部 URL への直接データ送信経路の開放といった致命的リスクが生じる。

---

## 5. 論点 4：最終決定「人間介在型 Web 検索支援（Human-Assisted Web Search）」

これまでの議論を踏まえ、**「利用規約上、AI に自動検索させても Web 版 Gemini 相当の表示しか許可されないのであれば、検索実行そのものはユーザーが自身のブラウザで行い、Gemio は検索クエリの提案と貼り付け結果の診断・取り込み支援に徹する」** という方針を採ることに決定した。

### 本方式を採用した理由
* **利用規約リスクの完全解消:** Gemio から Google 検索や外部検索 API への自動アクセスを行わないため、Grounding 規約・スクレイピング規約・BYOK 所有要件のいずれにも抵触しない。
* **追加コスト・追加 API キー不要:** `GEMINI_API_KEY` 1本のみで完結するシンプルな体験を維持できる。
* **高い安全性:** 人間がブラウザ上で結果を目視確認し、必要な箇所だけを選別して貼り付けるため、機密流出と無差別な IPI 流入を構造的に抑制できる。

### 合意された最終設計仕様（決定事項）

| 項目 | 決定内容 | 補足・理由 |
| :--- | :--- | :--- |
| **1. コマンド体系の再編** | `/search` を廃止し、スイッチ専用の **`/web [on\|off]`** と資料管理用の **`/materials`** に再編する。 | 「Gemio が検索する」コマンドではなく「検索支援（`+WEB`/`-WEB`）と前提資料管理」であることを明確にするため。 |
| **2. `+WEB` / `-WEB` スイッチ** | ステータスヘッダーの `+WEB` / `-WEB` スイッチは維持する。 | `TRUST` モードでの自律作業中に検索協力モーダルで停止してしまうのを防ぎ、UX を損なわないようにするため。 |
| **3. 専用ダイアログの検索補助** | 専用モーダル（`UserSearchModal`）で推奨クエリの **`[Copy]`** と Google 検索の **`[Open]`** ボタンを提供する。**ただしコンテナ内起動（`in_container`）時は `[Open]` を非表示**とする。 | ユーザーが最小限の手間でブラウザ検索へ移れるようにしつつ、ブラウザ起動できないコンテナ内環境でのエラー・混乱を防ぐため。 |
| **4. 入力テキスト診断** | 貼り付けられたテキストをリアルタイム診断する。**機密情報（APIキー・秘密鍵等）検知時は送信をブロックして削除を促す**。**パス文字列検知時はブロックせず注意喚起のみ**行う。 | クリップボードの取り違えによる認証情報漏洩を確実に防止する一方、一般記事やメモ中のパス表記で作業が阻害されないようにするため。不可視文字の無害化や IPI/サイズ警告も併用する。 |
| **5. 応答形式の選択とタイトル** | **`[通常応答として送信]`** と **`[前提資料に追加して送信]`** を選べるようにする。前提資料登録時のタイトルは **AI が指定したタイトル** をそのまま使い、タイトル入力欄は設けない。 | 一時調査（後に `/compact` 圧縮）とセッション常駐参照を使い分けつつ、モーダル入力の手間を最小化するため。また、登録時は二重送信を避けて短い参照通知のみを返し、次イテレーションの `build_request_contents()` で同一ターン内に即反映させる。 |
| **6. `TRUST` モードの扱い** | `TRUST` モード中にユーザーがブラウザから外部テキストを貼り付けた場合でも、**モードはそのまま維持**する。 | ユーザー自身の目視選別・自己責任のもとで貼り付けたテキストであり、自律作業のテンポを維持するため。 |
