## 1. 全体像：多層防御（Defense in Depth）と2つの責任領域

AIエージェントにコード変更やシェルコマンド実行（`run_sandbox_command`）を許可する場合、単一の仕組みだけであらゆる脅威を防ぐことはできません。Gemioでは**「第1層：Pythonアプリケーション層（Gemio本体）」**と**「第2層：コンテナランタイム・OSカーネル層（Docker）」**の2層構造で安全性を担保しています。

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 【第1層】Pythonスクリプト側（Gemio本体: base.py / developer.py / agent.py） │
│  ・ユーザーのDocker設定ミスがあっても「最低限の致命的事故」を確実に阻止    │
│  ├─ ① ホストOS直接シェル実行の絶対禁止（実体ファイル /.dockerenv 検証）    │
│  ├─ ② 危険コンテナ（--privileged / docker.sock / --network host）の拒否   │
│  ├─ ③ ホスト側APIキー・トークン環境変数の自動除去（Scrubbing）            │
│  ├─ ④ ファイル操作ツールのパス境界検証＆機密ファイル（.env等）ハードブロック│
│  └─ ⑤ 承認プロンプト / サーキットブレーカー / タイムアウト＆プロセスキル   │
└────────────────────────────────────┬───────────────────────────────────────┘
                                     │ docker exec (承認されたコマンドの委譲)
                                     ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ 【第2層】Dockerコンテナ設定側（OSカーネル / Namespace / cgroups / Mounts） │
│  ・承認されたコマンドやテストコードが「内部で暴走・悪用」された場合を防御  │
│  ├─ ① ネットワーク隔離（--network none / host.docker.internal 遮断）      │
│  ├─ ② バインドマウント保護（.env マスクマウント / .git 読み取り専用化）    │
│  ├─ ③ リソース上限（--memory / --cpus / --pids-limit によるDoS防止）       │
│  ├─ ④ 権限最小化（非root -u 1000:1000 / --cap-drop=ALL / no-new-privileges）│
│  └─ ⑤ ファイルシステム保護（--read-only / --tmpfs noexec）                 │
└────────────────────────────────────────────────────────────────────────────┘
```

### 基本原則
* **Pythonスクリプト側の役割**:
  開発者がDockerの細かいセキュリティオプションを指定し忘れた場合でも、**「ホストOSの直接破壊」「コンテナ脱獄によるホスト乗っ取り」「AIの承認無視による暴走」を100%防ぐ最低限の安全網（セーフティネット）**として機能します。
* **Dockerコンテナ設定側の役割**:
  一度実行を許可されたシェルコマンド（例: `pytest` や `npm test`）の**プロセス内部で行われる挙動**（テストコード内に仕込まれた外部通信、メモリ大量消費、マウントされた `.env` の直接読み取りなど）をOSカーネルレベルで封じ込めます。

## 2. 第1層：Pythonスクリプト（Gemio本体）側で確保される安全性

Pythonスクリプト側（`src/gemio/project/base.py`, `src/gemio/project/developer.py`, `src/gemio/core/agent.py`）では、Docker側の設定に依存せず、以下の6つの安全性がコードレベルで常時保証されています。

### 2.1 ホストOS上でのシェル誤実行の100%阻止
* **実装箇所**: `DeveloperProject._is_running_in_container()` (`src/gemio/project/developer.py`)
* **仕組み**:
  偽装や誤設定が起きやすい環境変数（`DEVCONTAINER=true` 等）を一切信用せず、`sys.platform == "linux"` かつコンテナ実体ファイル（`/.dockerenv` または `/run/.containerenv`）が存在する場合のみ「コンテナ内」と判定します。
* **保証される安全性**:
  ホストOS（Windows / macOS / Linuxホスト）上で起動された場合は必ず `docker exec` によるコンテナ委譲モードとなり、**ホストOSのローカルシェル（PowerShellやホストのbash）が直接実行されるリスクはゼロ**です。

### 2.2 危険なDockerコンテナ構成の起動時強制ブロック (`SandboxSecurityError`)
* **実装箇所**: `_validate_and_configure_docker_container()`, `_validate_in_container_security()` (`src/gemio/project/developer.py`)
* **仕組み**:
  開発者モードの起動時に `docker inspect`（コンテナ内起動時は `/proc/1/status` 等）を解析し、以下の設定が1つでも検出された場合は `SandboxSecurityError` を送出して起動自体を拒否します。
  1. **特権モード（`--privileged`）**: `HostConfig.Privileged == True` または全ケーパビリティ有効状態の拒否。
  2. **Dockerソケット（`/var/run/docker.sock`）マウント**: コンテナ内からのホストDockerデーモン乗っ取りを阻止。
  3. **ホストネットワーク共有（`--network host`）**: ホストOSの全ローカルポート・ネットワーク空間の共有を拒否。
  4. **ホストルートマウント（`/`, `C:\`）**: ホストファイルシステム全体の露出を拒否。

### 2.3 環境変数（APIキー・各種トークン）の保護、両モード共通のキー名診断、およびメモリ保護
* **実装箇所**: `_detect_container_sensitive_env_keys()`, `_sanitize_inspect_info()`, `_disable_process_dumpable()`, `is_sensitive_env_key()`, `scrub_environment()` (`src/gemio/project/developer.py`), `prompt_api_key_for_container()` (`src/gemio/cli/ui.py`)
* **仕組み**:
  * **ホストOS起動時 (`host_docker`)**: LLM通信用の `GEMINI_API_KEY` はホスト側プロセスのメモリにのみ保持されます。また、`docker inspect` で取得したコンテナ設定の `Config.Env` は即座に値部分を `<redacted>` へマスクしてメモリ上に平文を残しません。
  * **コンテナ内起動時 (`in_container`)**:
    1. 環境変数に `GEMINI_API_KEY` / `GOOGLE_API_KEY` が未設定の場合は、起動時にOS別の環境変数確認・コピーコマンドを案内し、`****` マスク表示プロンプトで直接Pythonメモリ（`genai.Client(api_key=...)`）に受け渡します。
    2. `prctl(PR_SET_DUMPABLE, 0)` により、子プロセスから親プロセスのメモリ（`/proc/$PPID/mem` 等）を読み取る行為をカーネルレベルで遮断します。
  * **両モード共通のコンテナ内機密環境変数検査と強い警告通知 (`danger`)**:
    * `in_container`（`os.environ` / `/proc/1/environ`）および `host_docker`（マスク済み `Config.Env` / `docker exec` プローブ）の両方において、環境変数の「値」は一切読み取らずに非空の機密環境変数名（`is_sensitive_env_key`）のみを検出し、設定されている場合は起動時および `/sandbox` の診断パネルで `🔴 危険 (danger)` の強い警告を表示します。
  * **子プロセス起動時の自動スクラブ**:
    * **完全一致**: `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `AWS_SECRET_ACCESS_KEY`, `GITHUB_TOKEN`, `NPM_TOKEN`, `PYPI_TOKEN` 等
    * **末尾一致**: `*_API_KEY`, `*_SECRET`, `*_SECRET_KEY`, `*_TOKEN`, `*_PASSWORD`, `*_PRIVATE_KEY`

### 2.4 ファイル操作ツールにおけるパス境界・機密ファイル保護
* **実装箇所**: `_verify_and_get_path()`, `_check_fatal_security_path()`, `_verify_directory_tree_writable()` (`src/gemio/project/base.py`)
* **仕組み**:
  Gemio専用のファイル操作ツール（`read_file`, `write_file`, `delete_path`, `rename_path`, `search_text` 等）に対して、通常承認モード・トラストモードを問わず以下のハードブロックを適用します。
  * **パストラバーサル＆シンボリックリンク検証**: `Path.resolve()` と `is_relative_to()` により、プロジェクトルート外へのアクセスや、ルート外を指すシンボリックリンクの参照・操作を完全拒否。
  * **機密ファイル保護 (`SECRET_FILE_PATTERNS`)**: `.env`（`.env.example` 等のテンプレートを除く）、秘密鍵（`*.pem`, `*.key`, `id_rsa*` 等）、認証情報（`.npmrc`, `*credentials*.json`, `*.tfstate*`, `kubeconfig` 等）の読み書き・全文検索・ディレクトリごとの削除を拒否。
  * **管理・パッケージメタデータ領域の保護**: `.git/` 配下への直接ファイル操作、既存 `.devcontainer/` の改ざん・削除、および `*.egg-info/` の直接変更・削除を拒否。

### 2.5 Human-in-the-loop（承認モード）と暴走遮断（サーキットブレーカー）
* **実装箇所**: `Project._confirm()` (`src/gemio/project/base.py`), `AIChatAgent._execute_agent_loop()` (`src/gemio/core/agent.py`)
* **仕組み**:
  * **通常承認モード**: ファイル変更や `run_sandbox_command` の実行前に、操作内容・データ規模・プレビュー・実行コマンドを提示し、人間の承認（`y: 許可 / n: 拒否 / a: 強制中止 / k: プロセス終了`）を必須とします。
  * **サーキットブレーカー**: ユーザーが `n`（拒否）を選択したにもかかわらず、AIがユーザーへ報告・相談せずに連続して別の変更操作やコマンド実行を強行しようとした場合、自動的に `AgentExecutionAborted` を送出してエージェントの実行ループを強制終了します。

### 2.6 実行時間タイムアウト・プロセスキル・出力トランケート
* **実装箇所**: `run_sandbox_command()`, `truncate_command_output()`, `_kill_process()` (`src/gemio/project/developer.py`)
* **仕組み**:
  * コマンド実行にはデフォルト60秒（最大300秒）のタイムアウトが強制され、超過時は子プロセスを即座に `kill()` します。
  * 承認プロンプトで `k`（Kill）が選択された場合も、稼働中の子プロセスを道連れに即時キルします。
  * 標準出力・標準エラー出力が200行または10,000文字を超えた場合は中央を省略し、大量ログ出力によるコンテキスト溢れ（メモリ・トークン枯渇）を防ぎます。

## 3. 第2層：Dockerコンテナ設定側で確保すべき安全性（Python側の限界と補完）

Pythonスクリプト側で「コマンドを実行する前」の検査と制御は行われますが、**「承認されて実行が始まったコンテナ内シェル（`/bin/sh`）やテストプログラムが、コンテナ内部で何をするか」**はOSカーネルおよびDocker Engineの管轄となります。

以下の6点はPythonスクリプト側からは制御できないため、Dockerコンテナの設定（`docker run` オプションや `compose.yaml`）で確保する必要があります。

### 3.1 シェル・テストコード内部からの外部通信・データ漏洩の遮断 (`--network none`)
* **Python側の限界**:
  Python側は `--network host`（ホストネットワーク共有）はブロックしますが、通常のブリッジネットワーク（デフォルト設定）は許可します。もしブリッジ接続のまま悪意あるテストコードを実行すると、コンテナ内から外部サーバーへのデータ送信や、クラウドメタデータAPI（`169.254.169.254`）、`host.docker.internal` 経由でのホスト側ローカルサービスへのアクセスが可能になります。
* **Docker設定での対策**:
  * コンテナ起動時に **`--network none`**（Composeでは `network_mode: none`）を指定し、外部通信を物理的に100%遮断します（ホスト側でGemioを動かすため、コンテナがオフラインでもAI対話や `/search` は正常に機能します）。
  * やむを得ずブリッジ接続を使う場合は、**`--add-host=host.docker.internal:127.0.0.1`** を指定してホストOSへの通信経路を塞ぎます。

### 3.2 バインドマウント経由でのシェルによる機密ファイル・`.git` 迂回アクセス防止
* **Python側の限界**:
  Python側のガードレール（`_check_fatal_security_path`）は、Gemioのファイル操作ツール（`read_file` や `write_file`）に対して機能します。またシステムプロンプトでもシェル経由の機密ファイルアクセスを禁じています。
  しかし、`-v "$(pwd):/app"` でプロジェクト全体を読み書き可能でマウントしている場合、**技術的にはコンテナ内の `/bin/sh`（`cat /app/.env` 等）やテストスクリプト内部のPython/Node.jsコードから `/app/.env` を読み取ったり、`/app/.git/hooks` を書き換えたりすることがOSのファイル権限上可能**です。
* **Docker設定での対策**:
  * 開発対象のフォルダには原則として本番の `.env` や秘密鍵を配置しない。
  * ローカルに `.env` がある場合は、**`-v /dev/null:/app/.env:ro`** で空ファイルをオーバーレイマウント（マスク）し、コンテナ内から物理的に読めなくする。
  * コンテナ内でGit操作を行わない場合は、**`-v "$(pwd)/.git:/app/.git:ro"`** で `.git` ディレクトリを読み取り専用にする。

### 3.3 ハードウェアリソース枯渇・Fork爆弾の防止 (`--memory`, `--cpus`, `--pids-limit`)
* **Python側の限界**:
  Python側は「実行時間（最大300秒）」は制限できますが、その数十秒の間にコンテナ内のプロセスがメモリを数十GB確保したり、プロセスを無限増殖（Fork爆弾 `:(){ :|:& };:`）させたりしてホストOSをフリーズさせる挙動は、Pythonの `subprocess` からは制御できません。
* **Docker設定での対策**:
  * Linuxカーネルの `cgroups` 制限を有効にするため、**`--memory=2g`**、**`--cpus=2.0`**、**`--pids-limit=128`**（プロセス数上限）を必ず指定します。

### 3.4 コンテナ内root権限の排除とホスト側パーミッション汚染の防止 (`-u`, `--cap-drop`)
* **Python側の限界**:
  Python側は `--privileged`（特権モード）は弾きますが、通常のコンテナ内でデフォルトの `root` ユーザー（UID 0）が使われているかどうかまではブロックしません。コンテナ内 `root` で動作すると、万一カーネル脆弱性を突かれた際のリスクが高まるほか、Linux/WSL2環境では**コンテナ内で生成されたファイルがホスト側でも `root` 所有となり、一般ユーザーで削除・編集できなくなる問題**が起きます。
* **Docker設定での対策**:
  * **`-u 1000:1000`**（または Dockerfile の `USER` 命令）で非rootユーザーとして実行する。
  * **`--cap-drop=ALL`** で不要なLinuxケーパビリティをすべて剥奪し、**`--security-opt=no-new-privileges:true`** で `setuid` バイナリ等による権限昇格を禁止する。

### 3.5 システム領域改ざん・不正バイナリ実行の防止 (`--read-only`, `tmpfs`)
* **Python側の限界**:
  コンテナ内の `/usr` や `/tmp` などのシステム領域へのファイル書き込みは、ホストのプロジェクトディレクトリ外であってもコンテナ内部の書き込みとしては許容されます。
* **Docker設定での対策**:
  * より高い強度を求める場合は、**`--read-only`** でコンテナのルートファイルシステムを読み取り専用化し、一時領域は **`--tmpfs /tmp:rw,noexec,nosuid,size=64m`** でメモリ上に制限付き（バイナリ実行不可）でマウントします。

### 3.6 コンテナ自身への環境変数注入とイメージビルド時の機密混入防止
* **Python側の限界と診断補完**:
  Python側の `scrub_environment()` が消去できるのは「Gemioプロセス自身が持っている環境変数」だけです。ユーザーが `docker run -e SECRET_KEY=xxx` や `compose.yaml` の `env_file: .env` で**コンテナ起動時に直接コンテナへ注入した環境変数**や、**`docker build` 時に `COPY . .` でイメージ内に焼き込んだ機密ファイル**は、Python側からは消去できません（※ただし、コンテナ内の環境変数にAPIキーやトークンが設定されている場合は、`_detect_container_sensitive_env_keys()` が値を読み取らずキー名のみを検知し、診断パネル上で `🔴 危険` アラートとして強く警告します）。
* **Docker設定での対策**:
  * コンテナ起動設定（`compose.yaml` 等）に本番シークレットや `env_file: .env` を記述しない。
  * `.dockerignore` に `.env*`, `*.pem`, `*.key`, `*credentials*.json` 等を明記し、イメージへの機密ファイル混入を防ぐ。

## 5. 利用シナリオ別：どこまで設定すべきかの実践ガイドライン

すべての日々の開発で最高強度の重装備をする必要はありません。プロジェクトの信頼度と実行モードに合わせて、以下の3段階で運用するのが合理的です。

### レベル1：自作の信頼できるコードを「通常承認モード」で開発する場合
* **リスク特性**: コードに悪意（プロンプトインジェクション等）はなく、すべてのコマンド実行前に人間が確認（`y/n`）を行う。
* **必要な対策**:
  * **Pythonスクリプト側の自動検査 ＋ 非rootユーザー指定（`-u 1000:1000`）** だけで十分な安全性が確保されます。
  * 致命的なコンテナ設定ミスはPython側が起動時に弾き、AIの操作ミスは人間の承認確認とファイルガードレールが防ぎます。

### レベル2：自作コードを「トラストモード（`--trust`）」で高速に自律開発させる場合
* **リスク特性**: コードに悪意はないが、人間の承認確認をスキップしてAIが連続でテスト・コマンドを実行するため、「AIの思い込みによるうっかりミス」や「バグコードによる無限ループ・メモリリーク」に備える必要がある。
* **必要な対策**:
  * Python側のガードレールに加え、Docker側で **`--network none`（外部通信遮断）** と **リソース制限（`--memory=2g --cpus=2.0 --pids-limit=128`）**、および **非root指定（`-u 1000:1000`）** を適用します。
  * 作業前にGitの別ブランチ（`git checkout -b feature/...`）を切っておくことで、万一コードが壊れても `git reset` で即座に復元できます。

### レベル3：外部の未知のリポジトリ・第三者コードを検証する場合
* **リスク特性**: リポジトリ内のコメントやテストコードに悪意ある命令や情報窃取スクリプトが含まれている可能性がある。
* **必要な対策**:
  * **必ず「通常承認モード（`--trust` なし）」**で起動する。
  * Docker側で **`--network none`**、**`--cap-drop=ALL`**、**`--security-opt=no-new-privileges:true`**、**`--read-only` ＋ `--tmpfs`**、**リソース制限**をすべて適用する。
  * ホスト側に `.env` がある場合は **`-v /dev/null:/app/.env:ro`** でマスクし、**`-v "$(pwd)/.git:/app/.git:ro"`** で `.git` フックの改ざんを物理的に封じる。
