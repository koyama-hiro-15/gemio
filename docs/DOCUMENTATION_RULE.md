# 📄 設計書・技術ドキュメント運用ルール

**作成日:** 2026年10月31日  
**最終更新日:** 2026年11月17日  
**ステータス:** 運用中  
**対象範囲:** `docs/` および `manuals/` 配下のすべての設計書・技術仕様書・マニュアル  

### 【要約】
本プロジェクトにおけるドキュメント体系の役割分担（現行仕様の正と設計判断ログの分離）、`docs/design/` の3桁連番管理ルール、ライフサイクルを表すステータス定義（`実装完了（現行）` / `一部更新` / `置換済み` 等）、および新規作成・更新時の必須記載フォーマットを定めます。

---

## 1. 基本方針（Single Source of Truth と ADR型連番管理）

機能追加やリファクタリングを重ねてもドキュメントの二重管理や陳腐化が起きないよう、**「現在の最新構造（As-Is）」**と**「当時の設計判断・背景（Why / To-Be）」**の役割を明確に分離して管理します。

| ドキュメント種別 | 配置場所 | 役割・位置づけ | 保守方針 |
| :--- | :--- | :--- | :--- |
| **現行アーキテクチャ仕様** | [`manuals/07_ARCHITECTURE_REFERENCE.md`](../manuals/07_ARCHITECTURE_REFERENCE.md) | **現在のコード構造・内部仕様の唯一の正（Single Source of Truth）** | アーキテクチャや公開APIに変更があるたび、常に最新の実装と一致させる。 |
| **エンドユーザー / 開発ガイド** | `manuals/01_` 〜 `06_`, `08_`, `09_` | 利用方法・拡張開発レシピ・テスト手順 | 現行の操作方法・規約に合わせて最新に保つ。 |
| **設計書・技術資料インデックス** | [`docs/README.md`](./README.md) | `docs/` 全体の目次・ステータス一覧・ナビゲーション | 設計書や技術資料の追加・ステータス変更時に同期更新する。 |
| **個別機能・改修の設計書** | `docs/design/NNN_*.md` | **ADR（Architecture Decision Records）型の設計記録**<br>（解決した課題、採用した設計意図、代替案の検討記録） | 時系列の3桁連番で蓄積する。後続のリファクタリングが入った際も過去の本文は無理に書き直さず、**ヘッダーのステータス更新と注記追加**で軽量に管理する。 |
| **技術調査資料** | `docs/tech_docs/*.md` | 外部技術・コンテナ・セキュリティ境界の調査リファレンス | 必要に応じて追記・更新する。 |
| **開発履歴サマリー** | [`docs/PROJECT_SUMMARY.md`](./PROJECT_SUMMARY.md) | 時系列の改修作業ログ | 既存履歴は書き換えず、作業完了ごとに**末尾へ日付・バージョン付きで追記**する。 |

## 2. `docs/design/` の連番命名規則とライフサイクル管理

### 2.1 ファイル命名規則（3桁連番）
* `docs/design/` 配下の設計書は、作成順に **`NNN_<英語スネークケース名>.md`**（3桁ゼロ埋め連番、`001_` 始まり）で命名します。
  * 例: `001_web_search.md`, `013_core_package_refactoring.md`
  * ディレクトリ自体が `docs/design/` であるため、ファイル名先頭への `design_` の重複付与は不要です。
* 新規設計書を作成した際は、必ず **[`docs/README.md`](./README.md) の一覧テーブルにもエントリを追加**してください。
* 設計書間で他の設計書を参照する際は、`#013` や `` `[#013 Coreパッケージ構造リファクタリング](./013_core_package_refactoring.md)` `` のように連番を用いて簡潔・明確に記述します。

### 2.2 ステータスの定義
設計書のタイトル直下に記載する `ステータス` は、現在のコードベースとの関係を明確にするため以下の区分を使用します。

| ステータス表記 | 意味・適用基準 |
| :--- | :--- |
| **`ドラフト`** / **`レビュー待ち`** | 構想段階またはレビュー中の未確定設計。 |
| **`設計完了（実装準備中）`** / **`実装中`** | 設計が合意され、これから実装を行う（または実装途中の）状態。 |
| **`実装完了（現行）`** | 実装が完了しており、主要なクラス構成・モジュール配置・仕様が現行コードと一致している状態。 |
| **`一部更新（#NNN 参照）`** | **機能の目的・基本仕様・UXは現在も有効**だが、内部のクラス配置や一部データ構造が後続のリファクタリング（`#NNN`）で移動・刷新された状態。 |
| **`置換済み（Superseded by #NNN）`** | 設計対象そのものが、後続の設計書（`#NNN`）によって全面的に再設計・置き換えられた状態（歴史的経緯の記録として保持）。 |
| **`運用中`** / **`技術資料`** | ルール文書、マニュアル、および `docs/tech_docs/` の技術調査資料に使用。 |

### 2.3 後続リファクタリング実施時の軽量メンテナンス手順
大規模なリファクタリング等によって過去の設計書に記載されたクラス名やファイル構成が変わった場合は、以下の手順で最小限の更新を行います（**過去の設計書の本文全体を書き直す必要はありません**）。

1. 該当する過去設計書の `最終更新日` を更新し、`ステータス` を `一部更新（#NNN 参照）` または `置換済み（Superseded by #NNN）` に変更する。
2. 要約セクションの下（またはヘッダー直下）に、以下のような1〜2行の注記ブロックを追加する：
   ```markdown
   > **💡 現行仕様に関する注記:** 本設計の基本仕様は現在も有効ですが、内部クラス構成（旧 `AIChatAgent` 等）は後続の [`013_core_package_refactoring.md`](./013_core_package_refactoring.md) で刷新されています。現行の正確なモジュール構造は [`manuals/07_ARCHITECTURE_REFERENCE.md`](../../manuals/07_ARCHITECTURE_REFERENCE.md) を参照してください。
   ```
3. 末尾の `更新履歴` テーブルにステータス変更の旨を追記し、[`docs/README.md`](./README.md) の一覧表のステータス欄を同期する。

### 2.4 開発者およびAIエージェント向けの参照ルール
* コード改修や仕様確認のために `docs/` を参照する際は、**最初に [`docs/README.md`](./README.md) と各ファイル先頭の `ステータス`・注記を確認**してください。
* `一部更新` または `置換済み` となっている設計書を読む際は、「なぜその仕様が必要になったか（背景・課題・安全上の意図）」の理解に活用し、記載されている当時の旧クラス名や旧ファイルパスを現行仕様と誤認しないよう注意してください（現行構造の確認には必ず最新のソースコードおよび [`manuals/07_ARCHITECTURE_REFERENCE.md`](../manuals/07_ARCHITECTURE_REFERENCE.md) を参照すること）。

## 3. 必須記載ルールと標準テンプレート

### 3.1 新規作成時の必須項目
設計書・技術ドキュメントを作成する際は、**タイトル直下（上部）**に以下のメタデータおよび要約を必ず記載してください。
1. **作成日 / 最終更新日**: `YYYY年MM月DD日` 形式で明記する。
2. **ステータス**: 2.2節の区分に従って記載する。
3. **対象システム**: 影響を受けるファイルパスやパッケージ。
4. **【要約】(Summary)**: その設計書の目的、解決する課題、提案する仕様の要点を2〜4行程度で端的に記述する。

### 3.2 更新時の必須項目
既存のドキュメントに変更を加えた場合は、以下の対応を必ず行います。
1. **最終更新日の更新**: タイトル直下の `最終更新日` を当日の日付に更新する。
2. **ステータス・要約の同期**: 仕様変更や後続リファクタリングに応じてステータス・注記・【要約】を更新する。
3. **更新履歴（Changelog）の追記**: ドキュメント末尾の「更新履歴」テーブルに更新日付（`YYYY-MM-DD`）・ステータス・変更内容の要約を追記する。

### 3.3 ヘッダー＆更新履歴 標準テンプレート

新規に設計書（`docs/design/NNN_*.md`）を作成する際は、以下のテンプレートを使用してください。

```markdown
# #NNN 〇〇機能 設計書

**作成日:** YYYY年MM月DD日  
**最終更新日:** YYYY年MM月DD日  
**ステータス:** 設計完了（実装準備中）  
**対象システム:** `src/gemio/...`  

### 【要約】
（ここに本設計書の目的、対象機能、主な仕様や解決する課題の要約を2〜4行程度で記載してください）

---

## 1. 背景と解決すべき課題
...

---

## 更新履歴

| 日付 | 更新者 | ステータス | 変更内容の要約 |
| :--- | :--- | :--- | :--- |
| YYYY-MM-DD | AI Agent | 実装完了（現行） | 初版作成および実装の完了を反映 |
```
