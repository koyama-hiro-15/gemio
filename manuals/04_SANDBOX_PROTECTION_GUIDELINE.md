## 1. 基本原則：「部屋の中」はAI、「部屋の壁と鍵」は人間

Dockerサンドボックスは、AIエージェントに与える**「安全な作業部屋」**です。何をAIに編集させてよいか迷ったときは、対象のファイルが**「部屋の中の仕事道具・成果物」**なのか、それとも**「部屋の壁・鍵・ルールそのもの」**なのかで区分します。

* **🟢 AIに編集させてよいもの（＝部屋の中の仕事道具・成果物）**
  * **対象**: プログラムのソースコード（`src/`）、テストコード（`tests/`）、設計書・ドキュメント（`docs/`, `*.md`）
  * **理由**: 万が一AIが誤ったコードを書いても、`git diff` で差分を確認でき、`git checkout` や `git reset` で**即座に元の状態へ巻き戻せるため**です。
* **🔒 人間が管理し、保護すべきもの（＝部屋の壁・鍵・タイムマシン）**
  * **部屋の壁とエージェント規則（サンドボックス・拡張設定）**: `Dockerfile`, `compose.yaml`, `.dockerignore`, `.devcontainer/`, `.gemio/`
  * **持ち込む道具の許可リスト**: `requirements.txt`, `pyproject.toml`（他言語では `package.json`, `Cargo.toml`, `go.mod` 等）
  * **タイムマシン（履歴と巻き戻し機能）**: `.git/`, `.gitignore`
  * **金庫の鍵（機密情報・個人メモ）**: `.env`, 秘密鍵, クラウド認証情報, `memo/`
  * **理由**: AIが「テストを通すために設定を変えよう」「パッケージを勝手に入れ替えよう」「Gitフックや履歴を書き換えよう」としてこれらを変更してしまうと、**安全の壁が壊れたり、変更を元に戻せなくなったりするため**です。

## 2. 重要知識：Dockerで `:ro`（保護）にしてもAIへの相談・編集依頼は可能

GemioをホストOS側で起動してDockerコンテナに接続している場合（Host-Orchestrated モード）、**AIがファイルに触る経路は2つ**に分かれています。

1. **コンテナ内のシェルコマンド（`run_sandbox_command` / `pytest` 等）**
   * Dockerコンテナ内部で動くため、`compose.yaml` の `:ro`（読み取り専用マウント）によって**OSレベルで物理的に書き換えが阻止**されます。
2. **Gemioの専用ファイル操作ツール（`write_file`, `search_and_replace_file` 等）**
   * ホストOS側のプロセスで動くため、人間が明示的に「`pyproject.toml` に設定を追加して」と指示し、**承認確認プロンプト（`y/n`）で人間が `y` を押したときだけ**書き込むことができます（※ただし `.env` 等の機密ファイルや `.git/`、既存 `.devcontainer/` は専用ツールでも常時ハードブロックされます）。

### この仕組みのメリット
`compose.yaml` で設定ファイル類をすべて `:ro`（読み取り専用）にしておけば：
* **普段のテスト実行やスクリプト実行中に、裏で勝手に設定ファイルを書き換えられる事故は100%防げる**
* **必要に応じてAIに記述内容を相談したり、人間の承認（`y`）のもとで編集を手伝ってもらうことはそのまま可能**

つまり、**「迷ったら `:ro`（読み取り専用）に入れておく」**のが最も安全かつ実用的なベストプラクティスです。

## 3. ファイルの4分類とDockerマウント保護基準（仕分け表）

プロジェクト内のファイル・フォルダを以下の4つのカテゴリに分類して設定します。

| 分類 | 対象ファイル・フォルダ | コンテナ内での権限 | 設定方法（`compose.yaml` 等） | 保護の目的 |
| :--- | :--- | :---: | :--- | :--- |
| **① AIの作業領域** | `src/`<br>`tests/`<br>`docs/`<br>`*.md` | **読み書き可 (`rw`)** | `- .:/app`（ベースマウントのまま） | AIが日常的にコード実装・テスト作成・ドキュメント更新を行う領域。 |
| **② 人間が管理する設定・管理領域** | `.git/`<br>`.gitignore`<br>`Dockerfile`<br>`compose.yaml`<br>`.dockerignore`<br>`.devcontainer/`<br>`.gemio/`<br>`requirements.txt`<br>`pyproject.toml` | **読み取り専用 (`ro`)** | 個別に `:ro` でオーバーレイマウント<br>例: `- ./Dockerfile:/app/Dockerfile:ro` | AIが設定を参照することは許可しつつ、シェルやスクリプトからの改ざんをOSレベルで禁止。 |
| **③ ホストと混ぜない環境領域** | `.venv/`<br>（他言語の `node_modules/` 等） | **隔離（匿名ボリューム / 専用Volume）** | `- /app/.venv` | ホストOS側の仮想環境とコンテナ内のLinux環境が混ざって壊れる（バイナリ競合・汚染）のを防止。 |
| **④ AIに見せない機密・個人領域** | `.env`, `.env.*`<br>秘密鍵・認証情報<br>`memo/`（個人メモ） | **完全遮断（マスク）** | ファイル: `- /dev/null:/app/.env:ro`<br>フォルダ: `tmpfs` マスク または配置しない | 書き換えだけでなく、コンテナ内から**中身を読み取られること自体**を物理的に防止。 |

*(※公開・共有用のテンプレートである `.env.example`, `.env.sample`, `.env.template`, `.env.dist` は機密を含まないため対象外です)*

## 4. 迷ったときの「たった1つの判断ルール」

今後、プロジェクトに新しいファイルやフォルダが増えた際に「これは保護すべきか？」と迷ったら、次の基準で判断してください。

> **Q. 「AIがテスト（`pytest` 等）を動かしている最中に、このファイルが勝手に書き換わったら困るか？」**
>
> 1. **書き換わってよい（むしろ直してほしい）**
>    👉 **① そのまま（`rw`）** にする（例: `src/`, `tests/`, `docs/`）
> 2. **勝手に書き換わったら困る（参照はしてよい）**
>    👉 **② `compose.yaml` で `:ro` を付ける**（例: 各種設定ファイル、ロックファイル、CI設定）
> 3. **ホストの環境と混ざると壊れる**
>    👉 **③ 匿名ボリュームで隔離する**（例: `.venv/`, `node_modules/`）
> 4. **そもそもAIに中身を見られたら困る**
>    👉 **④ `/dev/null` や `tmpfs` でマスクする、および `.dockerignore` に追加する**（例: `.env`, 秘密鍵, 個人メモ）

## 5. 標準Docker設定テンプレート（本プロジェクト基準）

上記の4分類を適用した、本プロジェクトの標準設定です。

### 5.1 `compose.yaml`（ボリュームマウント定義）
```yaml
    volumes:
      # ① AIが作業するベース領域（src/, tests/, docs/ 等は読み書き可能）
      - .:/app

      # ② 人間が管理する領域（コンテナ内では「読み取り専用 :ro」にして改ざん防止）
      - ./.git:/app/.git:ro
      - ./.gitignore:/app/.gitignore:ro
      - ./Dockerfile:/app/Dockerfile:ro
      - ./compose.yaml:/app/compose.yaml:ro
      - ./.dockerignore:/app/.dockerignore:ro
      - ./requirements.txt:/app/requirements.txt:ro
      - ./pyproject.toml:/app/pyproject.toml:ro
      # （プロジェクト直下に .gemio/ を作成した場合は以下も有効化して :ro 保護）
      # - ./.gemio:/app/.gemio:ro

      # ③ ホスト側と混ぜない仮想環境領域（匿名ボリュームで隔離）
      - /app/.venv

      # ④ AIに見せない機密領域（ホスト側に .env がある場合はコメントを外す）
      # - /dev/null:/app/.env:ro
```

### 5.2 `Dockerfile`（パッケージ・設定ファイルの所有者保護）
* `requirements.txt` のコピー時は `--chown=sandbox:sandbox` を付けず `root:root` 所有のままとし、`pip install` も `root` 権限で実行してから最後に `USER sandbox:sandbox`（UID 1000）へ切り替えます。
* これにより、万が一単体の `docker run` で個別 `:ro` マウントを忘れた場合でも、コンテナ内の非rootユーザー（AI）がインストール済みパッケージ（`/usr/local/lib/...`）を改ざん・アンインストールできない構造になります。

### 5.3 `.dockerignore`（イメージビルド時の混入防止）
* `src/gemio/project/base.py` の `SECRET_FILE_PATTERNS` および `SECRET_DIR_NAMES` と完全に同期させ、万が一 `Dockerfile` に `COPY . .` が記述された場合でも、機密ファイル（`.env*`, 秘密鍵, `.ssh`, `.aws`, `secrets.*`, `*.tfstate*` 等）や個人作業フォルダ（`memo/`）、仮想環境（`.venv/`）がDockerイメージのレイヤに焼き込まれないように保護します。
