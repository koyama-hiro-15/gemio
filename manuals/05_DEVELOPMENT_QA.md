## 1. モード選択・起動に関するQ&A

### Q1-1. 「基本モード」と「開発者モード (`--dev`)」は普段どう使い分ければいいですか？
* **A. 「テストやコマンドを実行させる必要があるか」で決めます。**
  * **基本モード（オプションなし）**:
    Dockerを起動したくない時、設計書やREADMEの作成、既存コードのリーディング、ちょっとしたPythonスクリプトの作成（`syntax_check` による文法確認のみで十分な場合）に使います。
  * **開発者モード（`--dev`）**:
    `pytest`、`npm test`、`cargo test`、`ruff`、`tsc` などの**テスト・Linter・ビルドコマンドを実際に走らせて、エラーが出たらAI自身に直させたい時**に使います。

---

### Q1-2. VS Codeの「Dev Container内」で起動するのと、「ホストOS」から起動するのはどちらが良いですか？
* **A. どちらの方式でもコンテナの環境変数にAPIキーを設定する必要はなく、両方とも安全に利用できます。開発スタイルに合わせて選んでください。**

  * **① ホストOS側のターミナルから起動する方式（Host-Orchestrated モード）**:
    ```bash
    # ホストOSのターミナルで実行（Dev Container自動検出 または --container 指定）
    python -m gemio . --dev
    ```
    * **メリット**:
      1. ホストOSのシステム環境変数（`GEMINI_API_KEY`）をそのまま読み込むため、起動時のAPIキー入力が不要です。
      2. コンテナを `--network none`（完全オフライン）にしても、ホスト側のGemioがGemini APIやWeb検索（`/search`）と通信できるため、**「ネット遮断されたコンテナ」と「AI対話・検索機能」を両立**できます。

  * **② VS Codeの「Dev Container内」ターミナルで起動する方式（In-Container モード）**:
    ```bash
    # Dev Container内の統合ターミナルで実行
    python -m gemio --dev
    ```
    * **メリット**:
      1. VS Codeの統合ターミナル内だけで画面を切り替えずに作業を完結でき、ホストOS側にPython環境を用意する必要がありません。
      2. コンテナの環境変数（`devcontainer.json` 等）にAPIキーを設定しなくても、**起動時にホストOSの別ターミナルからAPIキーを1回コピペしてマスク入力（`****`）する仕組み＋プロセスメモリ保護（`PR_SET_DUMPABLE=0`）**によって、コンテナ内のAIにAPIキーを読み取られるリスクを回避できます（もしコンテナ環境変数に各種APIキーが設定されている場合は、どちらの起動方式でも診断パネルで `🔴 危険` の強い警告として通知されます）。

### Q1-3. 毎回 `y`（許可）を押すのが大変です。`--edit`（エディットモード）と `--trust`（トラストモード）はどう使い分ければいいですか？
* **A. 普段の開発には「エディットモード（`--edit` / `/edit`）」が最もバランスが良く、完全自動でテスト修復まで回したい時に「トラストモード（`--trust` / `/trust`）」を使います。**
  * **🟡 エディットモード（`--edit` または対話中 `/edit`）が向いている時（日常開発におすすめ）**:
    ファイルの作成・編集・リネーム・コピーは自動承認されるためテンポよく実装が進み、一方で**ファイルの削除（`delete_path`）とシェルコマンド実行（`run_sandbox_command`）だけは事前に確認できる**安全な中間モードです。
  * **🔴 トラストモード（`--trust` または対話中 `/trust on`）が向いている時**:
    自分で作っている信頼済みプロジェクトで、Gitでいつでも元に戻せる状態のときに「テストが全部通るまで確認なしでコードを直してテストを回し続けてほしい」という場面に最適です。
  * **途中で切り替えるテクニック**:
    最初は通常承認モードや `/edit` でAIに修正方針を相談し、方針が固まったら **`/trust on`** で一気に自動実装・テストを走らせ、終わったら **`/trust off`**（または `/edit`）に戻す使い方が快適です。
  * **※注意**: GitHub等からクローンしたばかりの「まだ中身を読んでいない第三者のリポジトリ」では、通常承認モードで確認しながら進めてください。

### Q1-4. プロジェクト固有のコーディング規約や作業手順を毎回入力せずにAIに守らせたい時は？
* **A. プロジェクト直下に `.gemio/skills/<スキル名>/SKILL.md` を配置する「Skills機能」を使ってください。**
  * `.gemio/skills/` 配下に専門手順書（`SKILL.md`）を置いておくと、普段は「スキル名と1行説明」だけがAIに伝わり（トークンを節約）、関連する作業が始まったタイミングでAIが自動的に詳細手順を読み込んで作業を進めます。
  * また、`.gemio/tools/*.py` にプロジェクト固有のPython関数を置いてカスタムツールとして追加することも可能です。詳しい書き方は **[`06_SKILLS_AND_TOOLS_MANUAL.md`](./06_SKILLS_AND_TOOLS_MANUAL.md)** を参照してください。

## 2. パッケージ追加・ネットワーク制限（`--network none`）に関するQ&A

### Q2-1. `--network none` のコンテナ内で `pip install` や `npm install` をしたい時はどうすればいいですか？
* **A. 以下の2つの方法があります（おすすめは方法Aです）。**

  * **方法A（推奨）：`Dockerfile` や `requirements.txt` に追記してイメージを再ビルドする**
    1. Gemioに「`requirements.txt`（または `package.json`）に〇〇を追加して」と指示します。
    2. ホストOSの別ターミナルでコンテナイメージを再ビルドして起動し直します：
       ```bash
       # Docker Compose を使っている場合
       docker compose up -d --build
       ```
    * **メリット**: コンテナを一度もインターネットに繋ぐことなく、クリーンな状態を維持できます。

  * **方法B（一時的）：パッケージ導入時だけ一時的にブリッジネットワークを繋ぐ**
    ```bash
    # 1. ホスト側から一時的にデフォルトのbridgeネットワークを接続
    docker network connect bridge gemio-sandbox-py

    # 2. パッケージをインストール
    docker exec gemio-sandbox-py pip install pytest-cov

    # 3. 終わったら即座にネットワークを切断（オフラインに戻す）
    docker network disconnect bridge gemio-sandbox-py
    ```

---

### Q2-2. 外部API（StripeやOpenAI、外部Webサイト等）と通信するコードのテストはどうすればいいですか？
* **A. テストコード側で「モック（Mock）」を使うようにAIに指示してください。**
  * サンドボックスは `--network none` で外部通信を遮断するのが基本であるため、単体テストで本物の外部APIを叩く設計はアンチパターンになります。
  * **指示例**:
    ```text
    外部APIへの通信部分は unittest.mock（または pytest-mock / vi.spyOn）でモック化し、
    オフライン環境でもすべてのテストがパスするようにテストコードを作成してください。
    ```

---

### Q2-3. AIに最新のライブラリ仕様やドキュメントを調べさせながら実装してほしい時は？
* **A. ヘッダーが `+WEB`（デフォルトON）であれば、通常のプロンプトでそのまま指示すればAIが必要に応じて検索エージェントを呼び出します。**
  1. 通常のプロンプトでそのまま指示を出します：
     ```text
     FastAPI の最新の lifespan イベントの推奨記法を調べて、src/main.py の起動処理を書き換え、pytest を実行してください。
     ```
  2. AIが外部検索を行う際は、必ず事前に承認画面で**検索エージェントへ送信されるプロンプト全文**が表示されるため、非公開情報が含まれていないか確認して `Y` で許可できます。
  3. なお、対話履歴を汚さずに人間が直接調べたい時は `/search <調べたい内容>` で単発検索でき、セッション中ずっと参照させたい結果だけを `[+ 資料に追加]` ボタン（または `/search --save`）で「作業前提資料」に保持できます（破棄は `/search --clear`）。
  4. `TRUST` モードで完全放置実行したい場合など、検索確認で止めたくない時はヘッダーの `+WEB` をクリック（または `/search off`）して `-WEB` に切り替えてください。

## 3. 環境変数（`.env`）・機密情報の扱いに関するQ&A

### Q3-1. `.env` がブロックされて読めないと言われました。新しい環境変数を追加したい時はどうすればいいですか？
* **A. `.env.example`（テンプレート）をAIに編集させ、実際の `.env` への反映は人間が行います。**
  * Gemioはセキュリティ保護のため、`.env` は読み書き禁止ですが、**`.env.example` / `.env.sample` / `.env.template` / `.env.dist` は読み書きが許可**されています。
  * **おすすめの指示例**:
    ```text
    新しく追加した機能で必要な環境変数を `.env.example` にダミー値付きで追記してください。
    ```
  * その後、開発者自身の手で `.env.example` の内容を `.env` にコピーし、本物のキーを設定してください。

---

### Q3-2. テスト実行（`pytest` 等）にどうしてもダミーの環境変数が必要な場合はどう渡せばいいですか？
* **A. テストコード内（`conftest.py` や `monkeypatch`）で設定させるか、テスト用のコマンドラインでダミー値を渡させます。**
  * `.env` ファイルを使わなくても、以下のようにAIに指示すれば安全にテストが通ります：
    ```text
    テスト実行時に必要な環境変数（DATABASE_URL や API_KEY など）は、
    tests/conftest.py の fixture（monkeypatch.setenv）でダミー値をセットするようにしてください。
    ```

---

### Q3-3. すでにプロジェクト直下に本番キー入りの `.env` がある状態で、安全に `--dev` を使うには？
* **A. コンテナ起動時に `-v /dev/null:/app/.env:ro` を付けて `.env` をマスク（空ファイル化）してください。**
  ```bash
  docker run -d \
    --name gemio-sandbox-py \
    --network none \
    -u 1000:1000 \
    -v "$(pwd):/app" \
    -v /dev/null:/app/.env:ro \
    -w /app \
    my-gemio-env:latest sleep infinity
  ```
  * これにより、ホスト側の `.env` はそのまま残しつつ、**コンテナ内のシェルやテストコードから `.env` を見ると中身が空（0バイト）になる**ため、万が一にもキーが漏洩・改ざんされなくなります。

## 4. DB連携・Webサーバー・複数コンテナ構成（Docker Compose）のQ&A

### Q4-1. PostgreSQLやRedisなど、DBコンテナと連携して結合テストを回したい時は？
* **A. `compose.yaml` で **`internal: true`（内部専用ネットワーク）** を作ってDBコンテナと繋ぎます。**
  * `--network none` だと隣のDBコンテナとも通信できなくなりますが、Docker Composeで **`internal: true`** のネットワークを定義すると、**「インターネットやホストLANには一切出られないが、サンドボックスとテスト用DBコンテナの間だけで通信できる」**安全な隔離環境が作れます。

  #### `compose.yaml` の構成例（アプリ ＋ テスト用PostgreSQL）
  ```yaml
  services:
    sandbox:
      container_name: gemio-sandbox-app
      build: .
      user: "1000:1000"
      cap_drop: [ALL]
      security_opt: ["no-new-privileges:true"]
      mem_limit: 2g
      cpus: 2.0
      pids_limit: 128
      environment:
        - TEST_DATABASE_URL=postgresql://testuser:testpass@test-db:5432/testdb
      volumes:
        - .:/app
      working_dir: /app
      networks:
        - sandbox-internal-net
      command: sleep infinity

    test-db:
      image: postgres:16-alpine
      environment:
        - POSTGRES_USER=testuser
        - POSTGRES_PASSWORD=testpass
        - POSTGRES_DB=testdb
      networks:
        - sandbox-internal-net

  networks:
    sandbox-internal-net:
      # 外部インターネットへのルーティングを物理的に遮断する内部専用ネットワーク
      internal: true
  ```

### Q4-2. AIにWebサーバー（FastAPI / Next.js 等）を起動させて動作確認させたい時は？
* **A. フォアグラウンドで `uvicorn` や `npm run dev` を単体実行させるとタイムアウト（60秒）まで止まってしまうため、「テストクライアントを使う」か「1コマンド内でバックグラウンド起動＋疎通確認＋停止」を行わせます。**

  * **方法1（推奨）：フレームワーク標準のTestClientを使わせる**
    FastAPIの `TestClient`、Flaskの `test_client()`、Expressの `supertest` などを `pytest` や `vitest` から実行させれば、サーバーを常駐させずにミリ秒単位でエンドポイントの検証が可能です。
  * **方法2：1回のコマンド内で起動・`curl` 確認・停止を完結させる**
    どうしても実サーバーの起動確認をさせたい場合は、以下のように指示します：
    ```text
    サーバーをバックグラウンドで起動して数秒待ち、curl http://localhost:8000/health でレスポンスを確認したら、
    必ず同じコマンドの最後でサーバープロセスを kill して終了するように実行してください。
    ```

## 5. プロジェクト構成・多言語開発・パーミッションのQ&A

### Q5-1. フロントエンド（`frontend/`）とバックエンド（`backend/`）に分かれたモノレポ構成ではどう起動すればいいですか？
* **A. モノレポのルートディレクトリでGemioを起動してOKです。**
  * `run_sandbox_command` には `workdir`（作業ディレクトリ）引数があるため、AIは自動的に `workdir="frontend"` で `npm test` を実行し、`workdir="backend"` で `pytest` を実行できます。
  * もしフロントエンド用とバックエンド用で別々のDockerコンテナを動かしている場合は、今作業したい方のコンテナを `--container` で指定して起動してください。

---

### Q5-2. コンテナ内でAIが作ったファイルが `root` 所有になってしまい、ホスト側のVS Codeで保存・削除できません！
* **A. コンテナが `root`（デフォルト）で動いています。`-u $(id -u):$(id -g)`（または `user: "1000:1000"`）を指定してコンテナを起動し直してください。**
  * **すでに `root` 所有になってしまったファイルを直すコマンド（ホスト側のLinux / WSL2で実行）**:
    ```bash
    sudo chown -R $(id -u):$(id -g) .
    ```
  * **今後の再発防止**:
    `docker run` 時に `-u 1000:1000` を付けるか、`compose.yaml` に `user: "1000:1000"` を記載してください。

---

### Q5-3. ホストのMac/Windowsとコンテナで `node_modules` や `.venv` が競合してエラーになります。
* **A. OS依存のバイナリ（Linux用 vs Mac/Win用）が混ざっているのが原因です。匿名ボリュームでコンテナ専用領域に分離してください。**
  * ホスト側（MacやWindows）で作った `node_modules` や `.venv` をそのままLinuxコンテナにマウントすると、`esbuild` や `bcrypt`、`pydantic-core` などのネイティブ拡張が「Exec format error」で落ちます。
  * **解決策（`compose.yaml` の例）**:
    ```yaml
    volumes:
      - .:/app
      # コンテナ内の node_modules や .venv をホスト側と切り離す
      - /app/node_modules
      - /app/.venv
    ```

---

### Q5-4. WindowsやMacでコンテナ内のテスト実行やファイル検索がすごく遅い時は？
* **A. ファイルシステムの配置場所やDocker Desktopの設定を見直すと劇的に速くなります。**
  * **Windowsの場合**:
    `C:\Users\...` の下にプロジェクトを置くと、WSL2とWindows間のファイル変換で10倍以上遅くなります。**必ずWSL2（Ubuntu等）の中のLinuxディレクトリ（`~/projects/...`）にプロジェクトを置いてください。**
  * **macOSの場合**:
    Docker Desktopの「Settings > General」で **「VirtioFS」** にチェックを入れて有効化してください。

---

## 6. Git操作・ブランチ運用・設定ファイル保護のQ&A

### Q6-1. AIに `git commit` や `git push` までやらせてもいいですか？おすすめのGit運用は？
* **A. ブランチ作成やコミット・プッシュは「ホストOS側で人間が行う」のが最も安全で確実です。**
  * **理由**:
    1. コンテナにはSSH秘密鍵（`~/.ssh`）やGitHubトークンを渡さない設計にしているため、コンテナ内からの `git push` は認証エラーになります（それで正常・安全です）。
    2. Gemioは `.git/` ディレクトリの直接破壊を防止するガードレールを持っています。
  * **おすすめの黄金ワークフロー**:
    1. **【人間】** ホスト側で作業ブランチを切る（`git switch -c feat/add-login`）。
    2. **【Gemio】** `--dev --trust` で実装とテストを完了させる。
    3. **【人間】** ホスト側のVS Codeや `git diff` で変更内容を確認し、問題なければホスト側で `git commit` & `git push` する（もし気に入らなければ `git checkout .` で一発リセット）。

---

### Q6-2. 既存の `.devcontainer/devcontainer.json` をAIに修正させようとしたらエラーで拒否されました。
* **A. サンドボックス脱獄やエージェント設定の改ざんを防ぐためのセキュリティ仕様です。**
  * AIが勝手に `.devcontainer/devcontainer.json` を書き換えて `--privileged` を追加するような攻撃を防ぐため、**既存の `.devcontainer/` 配下（および `.gemio/` 配下のSkills・カスタムツール定義）はAIからの変更・削除がシステムレベルでロック**されています（※`.devcontainer/` がまだ存在しない状態での「新規作成」のみ許可されています）。
  * 既存の `.devcontainer/` や `.gemio/` を変更したい場合は、人間がエディタで直接編集するか、「変更案をチャット画面に出力して」とAIに指示してコピー＆ペーストしてください。

## 7. トラブル・暴走・緊急停止・コンテキスト管理に関するQ&A

### Q7-1. AIが同じテストエラーで何度もループして抜け出せなくなった時は？
* **A. 連続ループ上限（20回）で一時停止するか、承認画面で `a`（強制中止）を押してヒントを与えてください。**
  * AIが同じ箇所でハマっている時は、一度作業を止めて以下のように人間が方向性を修正してあげるとすぐに解決します：
    * 「一度変更を止めて、なぜテストが落ちているのか原因の仮説を3つ挙げて説明してください」
    * `/model argon` で上位の推論モデルに切り替えてから再度指示を出す。
    * `/search <エラーメッセージ>` で最新の解決策を単発検索し、`[+ 資料に追加]`（`/search --save`）で「作業前提資料」に入れてあげる。

---

### Q7-2. 承認画面の `n`（拒否）、`a`（強制中止）、`k`（プロセス終了）はどう使い分ければいいですか？
* **A. 止めたいレベルに応じて使い分けます。**
  * **`n` (拒否)**: 「そのファイルの消し方は危ないからやめて、別の方法を考えて（または一度説明して）」と**対話を続けたい時**。
    *(※もし `n` を押した後にAIが説明せず勝手に別の変更を強行しようとした場合は、サーキットブレーカーが自動で `a` と同じ強制中止を発動します)*
  * **`a` (強制中止 / Abort)**: 「今の指示自体を取り消したい」「今のAIの作業ループを即座に打ち切って、次の新しいプロンプト入力に戻りたい」時。**（Gemio自体は終了せず、対話履歴も保たれます）**
  * **`k` (プロセス終了 / Kill)**: 「今すぐすべてを強制終了してGemio自体を閉じたい」という**緊急停止ボタン**。実行中のコンテナ内サブプロセスも即座にキルしてプログラムを終了します。

---

### Q7-3. 実行したテストコマンドが固まって（ハングアップして）返ってこない時は？
* **A. 最大60秒（指定時は最大300秒）で自動的にタイムアウトして強制キルされます。**
  * テストコマンドの中で `input()` や ` [y/N]` のような**対話的な入力待ち**が発生していると、コマンドが終了せずタイムアウトになります。
  * タイムアウトエラーが出た場合は、AIが自動的に `--yes` や `-y` オプションを付けて再実行するか、対話入力をモック化するように修正します。

---

### Q7-4. 会話が長くなってプロンプト上部の `tokens: context` が黄色や赤になった時は？
* **A. 作業の区切りで `/clear`（または `/reset`）を実行して、新しい対話セッションに切り替えてください。**
  * 会話履歴が肥大化すると（🟡 `50,000` tokens 以上、🔴 `150,000` tokens 以上）、応答速度の低下や古い指示の忘却（Context Rot）、APIコストの増加につながります。
  * **`/tokens`** で現在のコンテキスト量と累積消費量の内訳を確認し、タスクがひと段落したら **`/clear`** を実行してください。
  * `/clear` は会話履歴とトークン統計をリセットしますが、`/search` で取得した「作業前提資料」や現在のモード・AIモデル設定はそのまま引き継がれます（前提資料も含めて全消去したい場合は **`/clear --all`** を使用します）。
