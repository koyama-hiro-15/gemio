# 📝 手動テスト（マニュアルテスト）ガイドライン

**作成日:** 2026年10月28日  
**最終更新日:** 2026年11月14日  
**ステータス:** 運用中  
**対象システム:** Gemio 全般 (`src/gemio/cli/`, `src/gemio/core/`, `src/gemio/project/`)  

### 【要約】
自動テスト（`pytest`）ではカバーできない実機体験（AI対話エージェント、対話型CLIキー操作、3段階承認・サーキットブレーカー・`ask_user` 双方向対話、Web検索連携、Dockerサンドボックス連携、Skills拡張など）について、品質を担保するために人間が手動で行うテスト（マニュアルテスト）のガイドラインおよび `git worktree` を活用した安全な検証手順書です。今後の動作確認や改修時のチェックリストとしてご活用ください。

---

## 1. テスト前の準備
手動テストを行う前に、必ず環境とテスト用プロジェクトの状態を確認してください。
- **環境確認**:
  - 仮想環境が有効化されていること。
  - ホストOSの環境変数 `GEMINI_API_KEY` にAPIキーが正しく設定されていること。
  - （開発者モード `--dev` を検証する場合）Docker Desktop / Engine が起動していること。
- **テスト用サンドボックスの用意**:
  - 実作業用のプロジェクトや本番環境を汚さないよう、適当な空のディレクトリ（例: `test_sandbox/`）を用意するか、一時的なテスト用プロジェクトを作成してください。

---

## 2. ワークツリーを使った安全なテスト手順

手動テスト（特にCLIのファイル作成・削除ツールや承認フロー）では、作業ディレクトリ内に一時ファイルが作成されたり、ファイルが実際に変更・削除されたりします。
`git worktree` を使うことで、**メインの作業ツリーや未コミットの変更を汚さずに完全な隔離環境でテスト・修正を行い、成果だけを元のブランチに安全に取り込む**ことができます。

### Step 1: テスト用コミットの作成（作業状態の保存）
手動テストを始める前に、現在の作業ブランチ（例: `main` や `feature/xxx`）の状態をコミットしてキリの良い状態にしておきます。
```bash
# 変更内容を確認
git status

# 現在の作業をコミットして保存（WIPコミットでも可）
git add .
git commit -m "test: 手動テスト実施前の作業状態を保存"
```

### Step 2: テスト用ワークツリーの作成と移動
プロジェクトルートから、1つ上の階層に新しいブランチとワークツリーを作成し、そちらへ移動します。
```bash
# 新規ブランチ（例: test/manual-check）を作成して別ディレクトリに展開
git worktree add ../manual-test-env -b test/manual-check

# 作成したテスト用ワークツリーへ移動
cd ../manual-test-env
```
> **Note**: 必要に応じて、仮想環境の有効化や環境変数 `GEMINI_API_KEY` の確認を行ってください。

### Step 3: 手動テストの実施と修正・コミット
隔離されたワークツリー側で、次節のテストケースを実施します。
不具合が見つかった場合はその場で修正し、コミットします。
```bash
# CLIの起動・手動テストを実施
python -m gemio

# 不具合を修正した場合、コミットを記録
git add .
git commit -m "fix: 手動テストで発見された〇〇の不具合を修正"
```

### Step 4: 元のディレクトリへ戻り、元のブランチへマージ
テストおよび修正が完了したら、元のディレクトリに戻り、作業ブランチへテスト結果（修正内容）を取り込みます。
```bash
# 1. 元のプロジェクトディレクトリに戻る
cd ../<元のプロジェクトフォルダ名>

# 2. 元の作業ブランチにいることを確認（必要なら switch）
git switch <作業ブランチ名>

# 3. テスト・修正ブランチをマージ
git merge test/manual-check
```

### Step 5: ワークツリーの後片付け（クリーンアップ）
手動テスト用のワークツリーと、マージが完了したブランチを削除して整理します。
```bash
# 1. ワークツリーを削除（テスト環境ディレクトリごと安全に削除されます）
git worktree remove ../manual-test-env

# 2. マージ済みのテストブランチを削除
git branch -d test/manual-check

# 3. 手動でワークツリーのディレクトリを削除した場合の管理情報の掃除
git worktree prune
```

## 3. テストケース一覧

### 🟢 テストグループ A: CLIの起動・入力操作・セッション管理
**目的**: アプリケーションがエラーなく起動し、複数行入力・クリア・各種スラッシュコマンド・終了処理が正しく機能するか確認する。

| No. | テスト項目 | 操作手順 | 期待される結果 |
| :--- | :--- | :--- | :--- |
| A-1 | **CLIの起動と `/help`** | 端末で `python -m gemio` を実行し、プロンプトで `/help` を送信する。 | ウェルカムバナーが表示され、`/help` で操作方法・全スラッシュコマンド一覧パネルが表示されること。 |
| A-2 | **複数行入力とクリア操作** | 複数行の文字を入力した状態で `[Esc]` ➔ `[Backspace]` を押す。その後、文章を再入力して `[Esc]` ➔ `[Enter]` を押す。 | `[Esc]`+`[Backspace]` で入力欄が全消去され、`[Esc]`+`[Enter]` でAIへの送信処理に移行すること。 |
| A-3 | **キーボード割り込み (Ctrl+C)** | ①プロンプト入力中に `Ctrl+C` を押す。<br>②AIの思考・ツール実行中に `Ctrl+C` を押す。 | ①入力がキャンセルされセッションが継続すること。<br>②トレースバックを出さず（子プロセス実行時は停止して）即座にプログラムが終了すること。 |
| A-4 | **モデル切替 (`/model`)** | `/model` を送信して番号選択、および `/model lite` を送信する。 | モデル選択パネルからの切替、およびエイリアス指定による即時切替が正常に行われること。 |
| A-5 | **トークン確認とセッションリセット (`/tokens`, `/clear`)** | 数回対話した後に `/tokens` を送信し、続けて `/clear` を送信する。 | `/tokens` でコンテキスト量と累積内訳が表示され、`/clear` で履歴とトークン統計が `0` にリセットされること。 |
| A-6 | **終了コマンド (`/exit`)** | プロンプトに `/exit`（または `exit`, `quit`）を入力して送信する。 | 終了メッセージが表示され、プログラムが正常に終了すること。 |

### 🟢 テストグループ B: AIエージェントとツール呼び出し (Function Calling)
**目的**: AIがユーザーの指示を理解し、適切なツール（ファイル操作・探索・日時取得・`ask_user` 等）を自律的に呼び出せるか確認する。

| No. | テスト項目 | 操作手順 | 期待される結果 |
| :--- | :--- | :--- | :--- |
| B-1 | **日時取得ツールの実行** | 「`今日の日付と現在の時刻を教えて`」と送信する。 | ログに日時取得ツール（`get_current_date`, `get_current_time`）の呼び出しが表示され、正確な現在日時を答えること。 |
| B-2 | **ファイル作成と構文チェック** | 「`hello.py` に挨拶関数を書いて構文チェックして」と送信する。 | `write_file`（承認確認後）および `syntax_check` が順番に呼び出され、正常にファイルが作成されること。 |
| B-3 | **階層探索ツールの実行** | 「`プロジェクトの構成を教えて`」と送信する。 | `get_structure` ツールが呼び出され、除外領域（`.git`, `.venv` 等）を除いた構成一覧が回答されること。 |
| B-4 | **`ask_user` 双方向確認パネル** | 「`仕様が2通り考えられる簡単なツールを作りたいので、まず私に方針を質問して`」と送信する。 | 「💬 Gemioからの確認・質問」パネルが選択肢付きで表示され、番号選択（または `0` 自由入力）で回答するとその方針で作業が進むこと。 |
| B-5 | **連続実行上限の確認** | 連続ループ上限に達する指示を与える（または上限設定を下げて検証）。 | 上限到達時に継続可否と追加ループ回数を尋ねるプロンプトが表示され、継続・中断が正常に動作すること。 |

### 🟢 テストグループ C: 3段階の承認モードと暴走防止機構 (Human-in-the-loop)
**目的**: 4択承認（`y`/`n`/`a`/`k`）、エディットモード、トラストモード、およびサーキットブレーカーが意図通り動作するか確認する。

| No. | テスト項目 | 操作手順 | 期待される結果 |
| :--- | :--- | :--- | :--- |
| C-1 | **承認4択の拒否 (`n`) と許可 (`y`)** | 通常承認モードで「`hello.py` を削除して」と指示し、初回は `n`（拒否）、再度指示して `y`（許可）を入力する。 | `n` では削除されずAIへ相談指示が返り、`y` ではファイルが正常に削除されること。 |
| C-2 | **強制中止 (`a`) の動作** | 複数ファイルの変更を指示し、1つ目の承認パネルで `a` を入力する。 | 現在のAI作業ループがその場で即座に打ち切られ、エラー終了せず次のプロンプト入力待ちに戻ること。 |
| C-3 | **エディットモード (`/edit`) の動作** | `/edit` で有効化した後、「`memo.txt` を作成し、その後削除して」と指示する。 | `write_file`（作成）は確認なしで自動承認され、`delete_path`（削除）のときだけ承認確認パネルが表示されること。 |
| C-4 | **トラストモード (`/trust`) の動作** | `/trust on` を実行して同意確認に `y` で答え、ファイル作成・削除を指示する。 | 同意確認パネルが表示された後、機密領域以外のファイル作成・削除がすべて自動承認されること。 |
| C-5 | **機密領域の常時ハードブロック** | トラストモード有効中に「`.env` を読み込んで」または「`.gemio/test.txt` を作って」と指示する。 | トラストモードであっても `[SECURITY_ALERT]` によりシステムレベルで確実にブロックされること。 |

### 🟢 テストグループ D: Web検索機能と作業前提資料連携 (`/search`)
**目的**: `/search`（`/s`）による隔離Web検索、出典表示、深掘り検索、作業前提資料としての蓄積・先頭注入・破棄が機能するか確認する。

| No. | テスト項目 | 操作手順 | 期待される結果 |
| :--- | :--- | :--- | :--- |
| D-1 | **検索コマンド (`/search`, `/s`) の実行** | 「`/search Python 最新の型ヒント機能`」を送信する。 | 検索スピナー表示後、回答と参照元リンクが表示され、「作業前提資料 [第1弾] として保持」の案内が出ること。 |
| D-2 | **引数なし時のヘルプ表示** | 「`/search`」のみを送信する。 | 検索は走らず、オプション（`-n`, `--clear`）を含む使い方パネルが表示されること。 |
| D-3 | **コマンド付け忘れ時の案内** | コマンドなしで「`最新のFastAPIのリリース情報を教えて`」と送信する。 | AIが推測で答えず、`/search` または `/s` を付けて送信するよう案内すること。 |
| D-4 | **連続深掘り検索と `-n` 新規検索** | D-1直後に「`/s 具体例を教えて`」を送信し、次に「`/s -n Go言語の最新動向`」を送信する。 | 1回目は深掘り検索スピナーで文脈を引き継ぎ、`-n` 指定時は初回検索スピナーで新規検索になること。 |
| D-5 | **作業前提資料のインジェクションと破棄** | 検索後に通常プロンプトで「`今の検索内容をもとにサンプルを書いて`」と指示し、完了後に `/search --clear` を実行する。 | 検索資料を踏まえたコード生成が行われ、`/search --clear`（または `/clear --all`）で保持資料が破棄されること。 |
